# 機体

`assets/upstream/f18/`、`tools/ac3d-to-glb.mjs`、`src/render/aircraft/` の中身を、原理と実装の対応で説明する。

機体は自前でモデリングしていない。FlightGear FGAddon の F/A-18C（作者 Fabrice Kauffmann、GPLv2+）を取り込んだ。判断の経緯は `docs/decisions/0005-aircraft.md` にある。

## 取り込みの流れ

原本を `assets/upstream/f18/` にコミットし、`npm run assets` が 2 本のツールを走らせて `public/aircraft/` を作る。ビルド時にネットワークを叩かない。

| ツール | 入力 | 出力 | ビルドで走るか |
|---|---|---|---|
| `tools/ac3d-to-glb.mjs` | `f18.ac`（AC3D、1,036,415 バイト） | `public/aircraft/f18.glb`（1,001 KB） | 走る |
| `tools/sgi-to-webp.py` | `f18top.rgb` ほか 3 枚（SGI 512×512） | `assets/generated/f18/` に WebP 3 枚（65 KB） | 走らない |

原本をコミットする理由は 2 つある。ビルド時にネットワークを叩かないため。そして GPLv2 が改変に適した形式の提供を求めるからである。生成物の glb と WebP は改変に適した形式とは言えない。

テクスチャは SGI 形式で、ブラウザは読めない。Pillow が読めるので WebP へ落とす。840 KB が 65 KB になった。

Pillow をビルドの経路に入れてはいけない。GitHub のランナーに入っていない。`npm run assets` から呼んだ最初の版は、CI が `ModuleNotFoundError: No module named 'PIL'` で落ちた。node は必ずある。Python の追加パッケージは違う。

変換結果を `assets/generated/f18/` にコミットして、ビルドでは `tools/ac3d-to-glb.mjs` が複製するだけにした。テクスチャが無ければ例外を投げ、走らせるコマンド名を出す。

## AC3D の形式

素のテキストで、行ごとにキーワードと値が並ぶ。依存パッケージは要らない。

```
AC3Db
MATERIAL "名前" rgb r g b  amb ...  emis ...  spec ...  shi n  trans t
OBJECT world
kids 87
OBJECT poly
name "LeftDoor_RearLeft"
texture "f18top.rgb"
loc x y z
numvert 8
（頂点が 8 行）
numsurf 6
SURF 0x30
mat 0
refs 4
（頂点番号 u v が 4 行）
kids 0
```

`SURF` のフラグは下位 4 bit が種類、`0x10` が滑らかな陰影、`0x20` が両面。原本の内訳は `0x0` が 6、`0x10` が 60、`0x20` が 6,597、`0x30` が 3,203。

多角形は 3 頂点から 32 頂点まで出てくる。扇状に割る。原本には凸でない面は無い。

`rot` `crease` `texrep` `url` `data` は原本に出てこないので実装していない。**出てきたら例外を投げる。**黙って無視すると形が崩れたまま気づけない。

### loc は親からの相対で、積み上げないと形にならない

`loc` を持つオブジェクトが 201 個のうち 144 個ある。親からの相対なので、木を降りながら積む必要がある。

積まずに測ると全長が 15.391 m になり、積むと 17.797 m になる。実機の F/A-18C は 17.07 m なので、積んだほうが正しい。計画を書いたときは積まずに測った値を「実測値」として記録していて、そのまま進めていたら 2.4 m 短い機体を作っていた。

翼幅は 11.571 m（公表値 11.43 m）、全高は 4.488 m（公表値 4.66 m）。3 軸すべて 5% 以内で一致するので、**このモデルは実寸である。**

## 座標系の突き合わせ

3 つの座標系が出てくる。

| 系 | 前 | 上 | 横 |
|---|---|---|---|
| `.ac` | −X | +Y | 左 +Z |
| `f18.xml`（FlightGear のモデル定義） | 後 +X | 上 +Z | 右 +Y |
| 当プロジェクト | −Z | +Y | 右 +X |

`.ac` から当方へは `our(x, y, z) = (−ac.z, ac.y, ac.x)`。行列式は +1 なので鏡像にならない。

XML との対応は**突き合わせで確定した。**`.ac` の `AileronLeft` が Z +3.742..+5.436 にあり、XML のヒンジが `y1 = −3.74241`、`y2 = −5.42703`。ここから `xml(x, y, z) = ac(x, −z, y)` が出る。当方の系へは `our(x, y, z) = xml(y, z, x)`。

推測ではなく数値の一致で決めた。`tests/tools/ac3d.test.ts` が 6 枚の舵面すべてで、XML のヒンジが対応する舵面の境界の内側に入ることを検査している。座標系を取り違えるとこの検査は必ず落ちる。

## 舵面

原本は舵面を名前つきの別オブジェクトとして持っている。`AileronLeft/Right`、`ElevatorLeft/Right`、`RudderLeft/Right`、`FlapsLeft/Right`、`Canopy_Glass`、それに降着装置の扉。

ヒンジの軸と舵角は `f18.xml` の rotate アニメーションに数値で入っているので、そのまま使う。

| 舵面 | ヒンジ（XML 座標） | 舵角 |
|---|---|---|
| エルロン | `x=2.67178, z=0.470943` の翼幅方向 | ±30° |
| ラダー | `(4.46901, ±1.03207, 0.670875)`–`(4.84972, ±1.39064, 1.71914)` | ±30° |
| エレベータ | 中心 `(5.22371, 0, −0.0314742)`、軸 `(0, 1, 0)` | ±25° |

変換ツールが舵面を独立したノードに切り出し、ノードの原点をヒンジの位置へ移す。頂点はそのぶん引く。こうしておくと描画側は回転を代入するだけで舵が切れる。

ヒンジの定義は glb の `scenes[0].extras.hinges` に載せてある。別ファイルにするとモデルと定義がずれる。同じ glb に入れておけば、変換ツールを直した時点で両方が変わる。

## ノードの分け方

| ノード | 中身 | 扱い |
|---|---|---|
| `body` | 胴体、主翼、尾翼、兵装 | 常に描く |
| 舵面 6 枚 | エルロン、エレベータ、ラダー | ヒンジまわりに回す |
| `gear` | 降着装置と扉 | 空中では隠す |
| `cockpit` | 操縦席の内装 | 外部視点では見えない |
| `ExternalFlame` | アフターバーナーの炎 | スロットル 0.85 超で出す |
| `InternalFlame` | ノズルの発光 | 常に描く |

アフターバーナーの炎は原本に入っている。FlightGear は `engines/engine[0]/augmentation` で `ExternalFlame` を出し入れし、`InternalFlame` は常に見せている。同じ扱いにした。

炎のマテリアルは `rgb 0,0,0` で `emis` だけを持つ。自発光を glTF の `emissiveFactor` へ写さないと、炎が黒い板になる。

## PBR の値の作り方

AC3D のマテリアルは Gouraud 時代の項目（`rgb` `amb` `emis` `spec` `shi`）しか持たない。テクスチャも拡散色だけ。PBR のマップは無いので、変換ツールが次の対応で埋める。

金属度は `spec` の平均。粗さは `1 − √(shi / 128)` を 0.1 から 0.95 で切る。`trans` が 0 でなければ `alphaMode` を `BLEND` にして、`baseColorFactor` のアルファを `1 − trans` にする。`emis` が 0.05 を超えたら `emissiveFactor` に写し、テクスチャがあれば `emissiveTexture` にも同じ画像を挿す。

名前で上書きする例外が 2 つある。`Glass` と `HUD` を含むものは金属度 0・粗さ 0.05。`Rubber` `LCD` `newmtl_0` `Black` は金属度 0・粗さ 0.8。

## 環境反射

機体は `MeshStandardMaterial` なので、金属の映り込みには環境マップが要る。HDRI を取り込むと出典管理が増えるうえ、時刻を変えても映り込みが変わらない。空から焼く。

`CubeCamera` で空のクアッドを 6 面に描き、`PMREMGenerator` で放射照度マップにして `scene.environment` へ入れる。焼くあいだは空以外を隠す。地形や機体が映り込むと自己参照になる。焼き直すのは時刻が変わったときだけなので、毎フレームの費用はない。

空のクアッドは頂点シェーダが position をそのままクリップ座標として使う全画面のもの。どのカメラでも画面を埋め、フラグメント側がカメラ行列から視線方向を作る。だから `CubeCamera` の 6 面それぞれで正しい方向が出る。

### 効き方を測る

環境反射の有無で差が出るのは画面の 1.67% だけ。最大差は排気口の内側で、明るさが 97 上がる。塗装面はほとんど動かない。地金は環境がないと黒くなるので、そこにだけ効くのが正しい振る舞い。

時刻でも変わる。ノズル内側の色は 12 時が青、17 時半が暖色。空の色をそのまま映している。

### 金属度を `spec` から決めてはいけない

AC3D のマテリアルは Gouraud 時代の項目しか持たない。`spec` は誘電体でも 1 になる「ハイライトの色」で、金属かどうかとは無関係。機械的に写すとパイロンとミサイルが金属度 1・粗さ 0.12 になり、環境反射を入れた瞬間に鏡と化す。実測でその画素がほぼ黒から空の色そのものへ跳ねた。

既定を誘電体にした。航空機で本当に金属なのは排気口の内側くらい。そこだけ名前で拾う。粗さの下限は 0.25。どこも鏡にならない値を選んだ。

## 影

影マップ 1 枚で機体の自己遮蔽と対地影の両方をまかなう。遮蔽物が機体だけなので、機体を囲む正射影の箱を太陽方向へ長く伸ばせば足りる。カスケードは要らない。

箱は 28 m 角。光源は機体から 400 m 手前に置く。`SunDirectionalLight` は `distance` と `target.position` から位置を決めるので、毎フレーム target を機体へ動かす。

機体は `MeshStandardMaterial` なので three の影がそのまま効く。地形と海面は自前シェーダなので、同じ深度テクスチャと `light.shadow.matrix` をユニフォームで渡し、`heightfield.glsl` に参照を足す。

### 影マップの種類は BasicShadowMap にする

`PCFShadowMap` は深度テクスチャに `compareFunction` を付ける（`WebGLShadowMap.js` の 263 行目）。すると `sampler2DShadow` でしか引けなくなる。`sampler2D` で引くと `GL_INVALID_OPERATION` が出る。メッセージは `Mismatch between texture format and sampler type`。そのドローコールごと捨てられ、地形と海面が丸ごと消えた。

`PCFSoftShadowMap` は three 0.185 で廃止されていて、指定すると警告を出して `PCFShadowMap` へ倒れる。倒れた先で上を踏んだ。

`BasicShadowMap` なら比較モードが付かず、ただの深度テクスチャとして引ける。縁が硬くなるが、地形側は自前で 2x2 の平均を取る。機体の自己遮蔽は 28 m の箱を 1024 px で割って 2.7 cm/テクセルなので、硬くても画面上では分からない。

切っているときも深度テクスチャを束縛したままにする。null を渡すと three は 1x1 の白い RGBA を束縛し、同じ型の食い違いが起きる。

### far 面に余裕を取る

影の落ちる地点がちょうど far 面に重なると、深度は 1.0 を超えて弾かれる。実測で海面にまったく影が出なかった。高度 222 m・太陽高度 30 度なら光路は 444 m。光源までの 400 m と足した 844 m を、そのまま far にしていた。

いまは地形が海面下 320 m まで下がることを見込んで 400 m 足し、さらに 200 m の余裕を取る。

### ユニフォームは描画のたびに入れ直す

影のテクスチャは three が最初の描画で作る。`sync()` で入れると 1 枚目が null のままになる。キャプチャモードは `sync()` が 1 回で描画が 8 回なので、影がまったく出ない。`render()` の頭で毎回入れ直す。

## コントレイルと翼端渦

履歴は sim が持つ。`Aircraft` に固定長のリングバッファを置き、4 フレームごとに 384 本（12.8 秒ぶん）記録する。描画側にバッファを置くと、キャプチャモードは `sync` が 1 回しか走らないので何も出ない。

サンプルには載せない。毎フレーム 384 本を写すのは無駄なので、描画は `Aircraft` から直接読む。読む側が要る形だけを `TrailSource` として切り出した。

出る条件は物理から決める。翼端渦は荷重倍数 3.5 から 6.5 で濃くなる。翼端の渦の中心で圧力が下がり、水蒸気が凝結する現象なので、荷重倍数をそのまま濃さに使う。コントレイルは気温が −40 度を下回る高度から。ISA だと 8,460 m より上なので、この機体の実用高度では滅多に出ない。

### リボンはカメラへ向けて立てる

翼端渦を機体上方向で立てると、真後ろから見たとき線に潰れて消える。進行方向と視線の両方に直交する向きを取れば、どこから見ても幅が残る。

### 1 点につき頂点は 3 個

左端・中心・右端で、濃さは端が 0、中心が最大。全体を同じ濃さにすると縁の硬い帯になり、水蒸気に見えない。区間ごとに 2 枚の帯を張るので三角形は 4 枚。

### 濃さは重なりを見込んで決める

1 画素ぶんの濃さがそのまま見た目になるわけではない。リボンは後方へ伸びるので、追従カメラからは長手方向に見る。1 本の視線が何区間も貫く。

実測。空との差から逆算すると 5 枚ぶん重なっていた。濃さの上限 0.22 でも空との差が 95 階調あり、白い筋に見える。0.10 で 71 階調、0.028 で 12.7 階調。

同じ断面（pull-up の frame 430、y=650）で測ると、上限 0.10 が 28.7 階調・断面の積分 1989、0.055 が 20.0・1417、0.028 が 12.7・976。**濃さを半分にしても見た目は半分にならない。**重なった層の合成 1−(1−a)^n が飽和するため。

### 濃さは経過秒で減らす。履歴の何本目かではない

以前は `(1 − i/(本数−1))²` で落としていた。描く本数を品質プリセットで変えると同じ絵が別の濃さになるうえ、画面に映る範囲ですでに 3 割ほど薄くなり、軌跡が空中で尻すぼみに消えた。

いまは経過秒で決める。翼端渦は寿命 16 秒、最初の 15% は濃さを保ち、そこから smoothstep で 0 へ。手前が持ちこたえるので、軌跡は薄れて消えるのではなく画面の縁で切れる。プリセットで変わるのは長さだけになった。

打ち切りの端だけは別に処理する。プリセットが履歴を途中で切ると濃さを残したまま断面が出るので、末尾 32 本（1.07 秒）を 0 へ落とす。

### 画面に映るのは 1 秒ぶんしかない

追従カメラは機体のすぐ後ろにいるので、軌跡はまたたく間にカメラの脇を過ぎて視錐台の外へ出る。

実測。`trailSegments` を 320 と 48 にして pull-up の frame 900 と 3000 を撮ると**画素が 1 ビットも違わない**。20 まで落とすと初めて崩れ、左の渦が丸ごと消える。つまり画面に出ているのは 20 本から 48 本のあいだ、1 秒弱・270 m ほど。

だから履歴を伸ばしても絵は伸びない。伸ばす意味は別のところにある。軌跡が途中で終わる原因を「履歴が尽きた」ではなく「画面の縁に達した」に固定できる。カメラを変える Phase 5 以降でも同じ性質が保たれる。

費用も測れる。**画素が一致するということは塗る量が同じ**ということなので、増えるのは頂点処理だけ。high の 192 本で 1 フレーム 1,728 頂点・2,292 三角形。

`?sweep=1` の GPU クエリ最小値。構図 1 は高 G で引き起こした瞬間（pull-up・フレーム 430）、構図 2 は低空で自分の影が地面に落ちている場面（low-pass・フレーム 2500）。

| 基準 | 4.81 ms | | 3.40 ms | |
| 後処理だけ | 1.73 | −3.08 | 1.45 | −1.95 |
| 雲なし | 2.38 | −2.43 | 2.88 | −0.53 |
| 機体なし | 4.17 | −0.64 | 3.31 | −0.09 |

## 描かれていないことをどう見つけるか

影を入れたときに地形が丸ごと消えた。原因にたどり着くまでに使った道具を残しておく。

`renderer.info` の `calls` と `triangles` を `TestHook` に出した。ただし `renderer.info` は `renderer.render()` ごとに 0 へ戻る。そのままでは最後のポストパスだけが残り、「ドローコール 1」に見える。`autoReset = false` にしてフレームの頭で消す。これで「地形は 438k 三角形ぶん投入されている」と分かり、**描かれていないのではなく描いた結果が捨てられている**と切り分けられた。

`git stash` で作業中の変更を外して撮り直し、基準画像と画素単位で比べた。HEAD では一致し、作業中では一致しない。ここで原因が作業中の変更にあると確定した。

**GL のエラーは Chrome のコンソールに `warning` として出る。**`error` だけを拾っていたので取りこぼしていた。`gl.getError()` を直接呼んで 1282 を得て、そこからコンソールの警告を洗い直した。計測スクリプトは `warning` も拾うようにしてある。

## 検算の考え方

自分のパーサが出した数値を自分で期待値に置くと、回帰しか防げない。正しさは外の事実と突き合わせて確かめる。使える外の事実が 3 つあった。

原本を素の正規表現で数えた値（201 オブジェクト、12,260 頂点、18,634 三角形、9,866 サーフェス）。FlightGear のアニメーション XML が持つヒンジの座標。実機の F/A-18C の寸法。

この 3 つをテストに書いてある。パーサを書き換えても、座標系を取り違えたり `loc` を落としたりすれば必ず落ちる。
