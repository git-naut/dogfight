# 機体

`assets/upstream/`、`tools/ac3d-to-glb.mjs`、`src/render/aircraft/` の中身を、原理と実装の対応で説明する。

機体は自前でモデリングしていない。FlightGear FGAddon から 2 機を取り込んだ。自機が F/A-18C（作者 Fabrice Kauffmann、GPLv2+）、敵機が F-16（GPLv2+、作者は `assets/CREDITS.md`）。判断の経緯は `docs/decisions/0005-aircraft.md` にある。

敵味方で別の機体にしたのは、ロックボックスが出ていない状態でも見分けられるようにするため。追従カメラの垂直画角は速度 250 m/s で 66.4 度あり、190 m の敵機は実測 20 画素にしかならない。塗装と輪郭が違えば、その大きさでも単垂直尾翼が 1 本か 2 本かで判別できる。

## 取り込みの流れ

原本を `assets/upstream/f18/` にコミットし、`npm run assets` が 2 本のツールを走らせて `public/aircraft/` を作る。ビルド時にネットワークを叩かない。

| ツール | 入力 | 出力 | ビルドで走るか |
|---|---|---|---|
| `tools/ac3d-to-glb.mjs` | `f18.ac`（AC3D、1,036,415 バイト） | `public/aircraft/f18.glb`（1,001 KB） | 走る |
| 同上 | `f16.ac`（AC3D、1,721,647 バイト） | `public/aircraft/f16.glb`（587 KB） | 走る |
| `tools/textures-to-webp.py` | `f18top.rgb` ほか 3 枚（SGI 512×512） | `assets/generated/f18/` に WebP 3 枚（65 KB） | 走らない |
| 同上 | `f16.png` ほか 3 枚（PNG、最大 2048×2048） | `assets/generated/f16/` に WebP 4 枚（436 KB） | 走らない |

機体ごとに違うところは `tools/aircraft-assets.mjs` が持つ。原本の場所、テクスチャの張り替え、舵面の名前と束ね方、降着装置の名前、空中で隠す部品。変換の手順は共通で、`ac3d-to-glb.mjs` はどの機体でも同じ処理を通す。id を引数に取れるので `node tools/ac3d-to-glb.mjs f16` で片方だけ作り直せる。

原本をコミットする理由は 2 つ。ビルド時にネットワークを叩かないため。そして GPLv2 が改変に適した形式の提供を求めるため。生成物の glb と WebP は改変に適した形式とは言えない。

テクスチャは SGI 形式で、ブラウザは読めない。Pillow が読めるので WebP へ落とす。840 KB が 65 KB になった。

Pillow をビルドの経路に入れてはいけない。GitHub のランナーに入っていない。`npm run assets` から呼んだ最初の版は、CI が `ModuleNotFoundError: No module named 'PIL'` で落ちた。node は必ずある。Python の追加パッケージは違う。

変換結果を `assets/generated/f18/` にコミットして、ビルドでは `tools/ac3d-to-glb.mjs` が複製するだけにした。テクスチャが無ければ例外を投げ、走らせるコマンド名を出す。

## AC3D の形式

素のテキストで、行ごとにキーワードと値が並ぶ。依存パッケージは要らない。

```
AC3Db
MATERIAL "名前" rgb r g b  amb ...  emis ...  spec ...  shi n  trans t
OBJECT world
kids 87
OBJECT poly
name "LeftDoor_RearLeft"
texture "f18top.rgb"
loc x y z
numvert 8
（頂点が 8 行）
numsurf 6
SURF 0x30
mat 0
refs 4
（頂点番号 u v が 4 行）
kids 0
```

`SURF` のフラグは下位 4 bit が種類、`0x10` が滑らかな陰影、`0x20` が両面。原本の内訳は `0x0` が 6、`0x10` が 60、`0x20` が 6,597、`0x30` が 3,203。

多角形は 3 頂点から 32 頂点まで出てくる。扇状に割る。原本には凸でない面は無い。

`crease` `texrep` `data` は F-16 の原本に出てくるので実装した（後述）。`rot` と `url` はどちらの原本にも無いので実装していない。**知らないキーワードが出てきたら例外を投げる。**黙って無視すると形が崩れたまま気づけない。

### loc は親からの相対で、積み上げないと形にならない

`loc` を持つオブジェクトが 201 個のうち 144 個ある。親からの相対なので、木を降りながら積む必要がある。積むと 201 個のうち 196 個が動き、最大の移動は 7.046 m（`ExternalFlame`）。

軸ごとに測ると、積むかどうかで変わるのは全高と全長。

| | 全長 | 全高 | 翼幅 |
|---|---|---|---|
| 積まない・全部 | 15.391 | 3.938 | 11.571 |
| 積む・全部 | 17.797 | 4.488 | 11.571 |
| 積む・機外の炎を除く | 15.391 | 4.488 | 11.571 |

**全長で判断してはいけない。**積んだときの 17.797 m と積まないときの 15.391 m の差 2.4 m は、`ExternalFlame`（機外に伸びる排気炎）1 つが作っている。機体だけの全長は積んでも積まなくても 15.391 m で変わらない。

積む必要があることは全高で分かる。3.938 m から 4.488 m へ伸び、公表値 4.66 m に対する比が 0.845 から 0.963 になる。翼幅は 11.571 m（公表値 11.43 m）で 1.012。

**全長は公表値と合わない。**機体だけで 15.391 m、公表値 17.07 m の 90.2%。翼幅と全高が 4% 以内で合うので縮尺は正しく、前後だけが詰まっている。F-16 も同じ傾向で、機体だけ 14.307 m、公表値 15.06 m の 95.0%。

以前この節には「3 軸すべて 5% 以内で一致するので、このモデルは実寸である」と書いてあった。**炎を含めた 17.797 m を公表値と比べていたためで、偶然合っていただけ。**F-16 を入れて検査を 2 機体で回したときに、炎を外した瞬間に 0.902 になって気づいた。テストも同じ比較をしていたので、寸法の裏取りとしては働いていなかった。いまは翼幅と全高を公表値と比べ、全長は実測値で固定して形が崩れたことだけを捕まえる。

## 座標系の突き合わせ

3 つの座標系が出てくる。

| 系 | 前 | 上 | 横 |
|---|---|---|---|
| `.ac` | −X | +Y | 左 +Z |
| `f18.xml`（FlightGear のモデル定義） | 後 +X | 上 +Z | 右 +Y |
| 当プロジェクト | −Z | +Y | 右 +X |

`.ac` から当方へは `our(x, y, z) = (−ac.z, ac.y, ac.x)`。行列式は +1 なので鏡像にならない。

XML との対応は**突き合わせで確定した。**`.ac` の `AileronLeft` が Z +3.742..+5.436 にあり、XML のヒンジが `y1 = −3.74241`、`y2 = −5.42703`。ここから `xml(x, y, z) = ac(x, −z, y)` が出る。当方の系へは `our(x, y, z) = xml(y, z, x)`。

推測ではなく数値の一致で決めた。`tests/tools/ac3d.test.ts` が舵面すべてで、XML のヒンジが対応する舵面の境界の内側に入ることを検査している。座標系を取り違えるとこの検査は必ず落ちる。

**この対応は F-16 でも別の証拠から確かめた。**同じとは限らないので突き合わせ直した。`.ac` の側では、ピトー管の位置が X −8.41..−7.64。垂直尾翼は X +2.81..+5.89 かつ Y +1.15..+3.19 にある。横方向は航法灯で決まる。`WingRedPosLight` は Z +4.49..+4.59、`WingGreenPosLight` は Z −4.60..−4.50。**灯火の約束では左舷を赤、右舷を緑にする。ここから +Z が左と決まる。**モデルの中の情報だけで向きを確定できる。

XML の側は `LeftUpperFlap` の中心が `(1.54, −2.35, 0.12)`。`.ac` の `LeftLowerFlap` は X 1.33..2.18 / Y 0.05..0.20 / Z 1.07..3.58。ラダーの中心 `(4.915, 0, 2.095)` と `.ac` の Rudder（X 4.31..5.89 / Y 1.15..3.03 / Z ≈ 0）でも成り立つ。

2 機で一致したので `tools/fg-coords.mjs` に 1 か所へまとめた。

## 舵面

原本は舵面を名前つきの別オブジェクトとして持っている。`AileronLeft/Right`、`ElevatorLeft/Right`、`RudderLeft/Right`、`FlapsLeft/Right`、`Canopy_Glass`、それに降着装置の扉。

ヒンジの軸と舵角は `f18.xml` の rotate アニメーションに数値で入っているので、そのまま使う。

| 舵面 | ヒンジ（XML 座標） | 舵角 |
|---|---|---|
| エルロン | `x=2.67178, z=0.470943` の翼幅方向 | ±30° |
| ラダー | `(4.46901, ±1.03207, 0.670875)`–`(4.84972, ±1.39064, 1.71914)` | ±30° |
| エレベータ | 中心 `(5.22371, 0, −0.0314742)`、軸 `(0, 1, 0)` | ±25° |

変換ツールが舵面を独立したノードに切り出し、ノードの原点をヒンジの位置へ移す。頂点はそのぶん引く。こうしておくと描画側は回転を代入するだけで舵が切れる。

ヒンジの定義は glb の `scenes[0].extras.hinges` に載せてある。別ファイルにするとモデルと定義がずれる。同じ glb に入れておけば、変換ツールを直した時点で両方が変わる。

## ノードの分け方

| ノード | 中身 | 扱い |
|---|---|---|
| `body` | 胴体、主翼、尾翼、兵装 | 常に描く |
| 舵面 6 枚 | エルロン、エレベータ、ラダー | ヒンジまわりに回す |
| `gear` | 降着装置と扉 | 空中では隠す |
| `cockpit` | 操縦席の内装 | 外部視点では見えない |
| `ExternalFlame` | アフターバーナーの炎 | スロットル 0.85 超で出す |
| `InternalFlame` | ノズルの発光 | 常に描く |

アフターバーナーの炎は原本に入っている。FlightGear は `engines/engine[0]/augmentation` で `ExternalFlame` を出し入れし、`InternalFlame` は常に見せている。同じ扱いにした。

炎のマテリアルは `rgb 0,0,0` で `emis` だけを持つ。自発光を glTF の `emissiveFactor` へ写さないと、炎が黒い板になる。

## PBR の値の作り方

AC3D のマテリアルは Gouraud 時代の項目（`rgb` `amb` `emis` `spec` `shi`）しか持たない。テクスチャも拡散色だけ。PBR のマップは無いので、変換ツールが次の対応で埋める。

金属度は `spec` の平均。粗さは `1 − √(shi / 128)` を 0.1 から 0.95 で切る。`trans` が 0 でなければ `alphaMode` を `BLEND` にして、`baseColorFactor` のアルファを `1 − trans` にする。`emis` が 0.05 を超えたら `emissiveFactor` に写し、テクスチャがあれば `emissiveTexture` にも同じ画像を挿す。

名前で上書きする例外が 2 つある。`Glass` と `HUD` を含むものは金属度 0・粗さ 0.05。`Rubber` `LCD` `newmtl_0` `Black` は金属度 0・粗さ 0.8。

## 環境反射

機体は `MeshStandardMaterial` なので、金属の映り込みには環境マップが要る。HDRI を取り込むと出典管理が増えるうえ、時刻を変えても映り込みが変わらない。空から焼く。

`CubeCamera` で空のクアッドを 6 面に描き、`PMREMGenerator` で放射照度マップにして `scene.environment` へ入れる。焼くあいだは空以外を隠す。地形や機体が映り込むと自己参照になる。焼き直すのは時刻が変わったときだけなので、毎フレームの費用はない。

空のクアッドは頂点シェーダが position をそのままクリップ座標として使う全画面のもの。どのカメラでも画面を埋め、フラグメント側がカメラ行列から視線方向を作る。だから `CubeCamera` の 6 面それぞれで正しい方向が出る。

### 効き方を測る

環境反射の有無で差が出るのは画面の 1.67% だけ。最大差は排気口の内側で、明るさが 97 上がる。塗装面はほとんど動かない。地金は環境がないと黒くなるので、そこにだけ効くのが正しい振る舞い。

時刻でも変わる。ノズル内側の色は 12 時が青、17 時半が暖色。空の色をそのまま映している。

### 金属度を `spec` から決めてはいけない

AC3D のマテリアルは Gouraud 時代の項目しか持たない。`spec` は誘電体でも 1 になる「ハイライトの色」で、金属かどうかとは無関係。機械的に写すとパイロンとミサイルが金属度 1・粗さ 0.12 になり、環境反射を入れた瞬間に鏡と化す。実測でその画素がほぼ黒から空の色そのものへ跳ねた。

既定を誘電体にした。航空機で本当に金属なのは排気口の内側くらい。そこだけ名前で拾う。粗さの下限は 0.25。どこも鏡にならない値を選んだ。

## 影

影マップ 1 枚で機体の自己遮蔽と対地影の両方をまかなう。遮蔽物が機体だけなので、機体を囲む正射影の箱を太陽方向へ長く伸ばせば足りる。カスケードは要らない。

箱は 28 m 角。光源は機体から 400 m 手前に置く。`SunDirectionalLight` は `distance` と `target.position` から位置を決めるので、毎フレーム target を機体へ動かす。

機体は `MeshStandardMaterial` なので three の影がそのまま効く。地形と海面は自前シェーダなので、同じ深度テクスチャと `light.shadow.matrix` をユニフォームで渡し、`heightfield.glsl` に参照を足す。

### 影マップの種類は BasicShadowMap にする

`PCFShadowMap` は深度テクスチャに `compareFunction` を付ける（`WebGLShadowMap.js` の 263 行目）。すると `sampler2DShadow` でしか引けなくなる。`sampler2D` で引くと `GL_INVALID_OPERATION` が出る。メッセージは `Mismatch between texture format and sampler type`。そのドローコールごと捨てられ、地形と海面が丸ごと消えた。

`PCFSoftShadowMap` は three 0.185 で廃止されていて、指定すると警告を出して `PCFShadowMap` へ倒れる。倒れた先で上を踏んだ。

`BasicShadowMap` なら比較モードが付かず、ただの深度テクスチャとして引ける。縁が硬くなるが、地形側は自前で 2x2 の平均を取る。機体の自己遮蔽は 28 m の箱を 1024 px で割って 2.7 cm/テクセルなので、硬くても画面上では分からない。

切っているときも深度テクスチャを束縛したままにする。null を渡すと three は 1x1 の白い RGBA を束縛し、同じ型の食い違いが起きる。

### far 面に余裕を取る

影の落ちる地点がちょうど far 面に重なると、深度は 1.0 を超えて弾かれる。実測で海面にまったく影が出なかった。高度 222 m・太陽高度 30 度なら光路は 444 m。光源までの 400 m と足した 844 m を、そのまま far にしていた。

いまは地形が海面下 320 m まで下がることを見込んで 400 m 足し、さらに 200 m の余裕を取る。

### ユニフォームは描画のたびに入れ直す

影のテクスチャは three が最初の描画で作る。`sync()` で入れると 1 枚目が null のままになる。キャプチャモードは `sync()` が 1 回で描画が 8 回なので、影がまったく出ない。`render()` の頭で毎回入れ直す。

## コントレイルと翼端渦

履歴は sim が持つ。`Aircraft` に固定長のリングバッファを置き、4 フレームごとに 384 本（12.8 秒ぶん）記録する。描画側にバッファを置くと、キャプチャモードは `sync` が 1 回しか走らないので何も出ない。

サンプルには載せない。毎フレーム 384 本を写すのは無駄なので、描画は `Aircraft` から直接読む。読む側が要る形だけを `TrailSource` として切り出した。

コントレイルが出る条件は気温が −40 度を下回る高度から。ISA だと 8,460 m より上なので、この機体の実用高度では滅多に出ない。

### 翼端渦は「マッハ数 × 揚力係数」で決める

判定は 2 度作り直した。どちらも「実装は動いているのに現象が出ない」形で外した。

**荷重倍数だと旋回で出ない。**閾値を 3.5 に置いていたが、この飛行モデルの定常旋回は 3.0 から 3.3 までしか出ない。逆に島へ向かう高速の引き起こしは 3.39 G で閾値の手前まで来る。速い引き起こしのほうが出やすい順になり、実機と逆になる。

**揚力係数だけだと速い引き起こしで出ない。**急上昇の実測は 6.86 G・340 m/s で揚力係数 0.453。速いほど揚力係数は下がるので、いちばん激しい機動がいちばん不利になる。実際に引き起こし直後の絵で渦が 1 階調しか出ていなかった。

芯の温度低下を無次元で書くと ΔT/T ∝ γM²Cl²/2 になる。マッハ数と揚力係数の**積**が駆動量で、どちらか片方では足りない。

| 場面 | 荷重倍数 | 速度 | M | Cl | M·Cl | 濃さ |
|---|---|---|---|---|---|---|
| 水平飛行（low-pass f2500） | 1.07 | 408 m/s | 1.20 | 0.044 | 0.053 | 0.00 |
| 高速の浅い引き起こし（island-run f2000） | 3.39 | 388 | 1.15 | 0.171 | 0.196 | 0.00 |
| 浅い旋回（bank-left f420） | 3.27 | 257 | 0.77 | 0.449 | 0.344 | 0.27 |
| 定常旋回（bank-left f1800） | 3.08 | 225 | 0.68 | 0.569 | 0.387 | 0.39 |
| 急上昇（zoom-climb f200） | 6.86 | 340 | 1.01 | 0.453 | 0.456 | 0.59 |
| 高 G の引き起こし（pull-up f900） | 5.92 | 269 | 0.82 | 0.710 | 0.582 | 0.95 |

閾値は 0.25 から 0.60。

**閾値が構図に届いているかを確かめないと、実装が動いていても現象が出ない。**2 度とも「リボンの実装がおかしい」と読み違えかけた。台本ごとに駆動量を表にして初めて分かった。

### 水蒸気は消えるのが遅い

**引くのをやめた瞬間に翼端の水蒸気が消えると、軌跡は切れ端になる。**画面に映るのは 0.7 秒ぶんもないので、機動が終わると同時に何も残らない。急上昇や急旋回で渦が短く見えたのはこれだった。

いったん凝結した水蒸気は渦核が崩れるまで残る。`Aircraft.wingtipVapor` を状態として持ち、駆動量へ非対称な一次遅れで追従させる。立ち上がり 0.2 秒、消えるのは 3.0 秒。

実測。`zoom-climb`（2 秒引いて舵を戻す）で、渦なしの版との差分から渦の画素だけを切り出した。

| 経過 | 遅れなし | 遅れあり |
|---|---|---|
| 舵を戻して 0.5 秒（f300） | 9 階調 | **27 階調** |
| 1.3 秒（f400） | — | 20 |
| 2.2 秒（f500） | — | 11 |
| 3.8 秒（f700） | — | 0 |

2 秒の引き起こしに対して 2.2 秒ぶん伸びた。合わせて画面に読める時間が 2 倍になる。

**画素の集計は背景の当て方で嘘になる。**最初は行の左右の中央値を背景に使ったが、地形と空のグラデーションまで拾って 3 万画素という値が出た。濃さ 0 の版を焼いて差分を取るのが正しい。

### リボンはカメラへ向けて立てる

翼端渦を機体上方向で立てると、真後ろから見たとき線に潰れて消える。進行方向と視線の両方に直交する向きを取れば、どこから見ても幅が残る。

### 1 点につき頂点は 3 個

左端・中心・右端で、濃さは端が 0、中心が最大。全体を同じ濃さにすると縁の硬い帯になり、水蒸気に見えない。区間ごとに 2 枚の帯を張るので三角形は 4 枚。

### 濃さは重なりを見込んで決める

1 画素ぶんの濃さがそのまま見た目になるわけではない。リボンは後方へ伸びるので、追従カメラからは長手方向に見る。1 本の視線が何区間も貫く。

実測。空との差から逆算すると 5 枚ぶん重なっていた。濃さの上限 0.22 でも空との差が 95 階調あり、白い筋に見える。0.10 で 71 階調、0.028 で 12.7 階調。

同じ断面（pull-up の frame 430、y=650）で測ると、上限 0.10 が 28.7 階調・断面の積分 1989、0.055 が 20.0・1417、0.028 が 12.7・976。**濃さを半分にしても見た目は半分にならない。**重なった層の合成 1−(1−a)^n が飽和するため。

### 濃さは経過秒で減らす。履歴の何本目かではない

以前は `(1 − i/(本数−1))²` で落としていた。描く本数を品質プリセットで変えると同じ絵が別の濃さになるうえ、画面に映る範囲ですでに 3 割ほど薄くなり、軌跡が空中で尻すぼみに消えた。

いまは経過秒で決める。翼端渦は寿命 16 秒、最初の 15% は濃さを保ち、そこから smoothstep で 0 へ。手前が持ちこたえるので、軌跡は薄れて消えるのではなく画面の縁で切れる。プリセットで変わるのは長さだけになった。

打ち切りの端だけは別に処理する。プリセットが履歴を途中で切ると濃さを残したまま断面が出るので、末尾 32 本（1.07 秒）を 0 へ落とす。

### 末端は「0 になる点からの距離」で先細りさせる

**直角に切り落とされて見える、という指摘を受けた。**実機の 5.44 G 旋回のスクリーンショット。いちばん太いところで断面が露出していた。

原因は先細りの数え方。以前は「描く本数の末尾 32 本」を落としていたが、**濃さが 0 になる境目は履歴の末尾だけにあるのではない。**水蒸気は 0.2 秒で立ち上がる。だから機動を始めた瞬間の位置に急な段差ができ、旋回を続けるとその段差が視界へ回り込む。

数え方を「0 になる点からの距離」に変えた。古いほうから新しいほうへ数え、0 に当たるたびにやり直す。履歴の打ち切りも「その先が 0」として同じ式で扱える。濃さだけでなく幅も絞る（消える手前は元の 35%）。太いまま薄くすると靄の塊に見える。

実測（同じ構図を再現して列ごとに測った）。

| 末端からの位置 | 幅 | 空との差 |
|---|---|---|
| x=920 | 0 px | 0 階調 |
| x=930 | 4 | 7 |
| x=940 | 8 | 14 |
| x=950 | 13 | 21 |
| x=960 | 17 | 24 |
| x=970 以降 | 22〜35 | 27 |

50 画素かけて幅と濃さがそろって 0 へ落ちる。

### near 面の手前で細く終端する

**空中で直角に切れる原因はこれだった。**リボンは翼端から後方へ伸びてカメラの脇を通り、near 面（`scene.ts` の 5 m）を越える。越えた三角形はラスタライザが near 面で切り、切り口の直線がそのまま画面に出る。濃さと幅が残ったままなので断面が露出する。

切り分けは消去法で付いた。**減衰と先細りを両方コードから外しても画素が 1 つも変わらない**（turn-in の frame 1000 で輪郭 4,700 画素・最悪 22 階調が一致）。つまり見えている範囲は全部「減衰なし」の領域で、端はリボンの終端ではない。残るのは視錐台の切り取りだけ。

**頂点を淡くするだけでは直らない。**クリップされた辺の色は両端の頂点から補間されるので、切り口には奥の頂点の濃さが乗る。実測でも距離フェードは効かなかった。

| 対処 | 断面（最悪） | 軌跡の平均濃さ |
|---|---|---|
| 何もしない | 22 階調 | 18.8 |
| 先細りを 32 → 250 本 | 12 | 全体が 14% 暗くなるだけ |
| 距離フェード 5→18 m | 19 | 9.1 |
| 距離フェード 5→30 m | 15 | 4.0 |
| **near 面の手前で終端** | **4〜5** | 1.8 |

淡くするのではなく、深度が 7 m を割る点で直前の点との間を割って、そこを最後の点にする。幅と濃さを 0 にするので、クリップが起きず細く消える。

**半径で測ってはいけない。**追従カメラは機体の 23 m 後方・6.8 m 上（`camera.ts` の OFFSET）なので、翼端の軌跡は 8.8 m まで近づく。半径 14 m で打ち切ると 3 点目で終わり、渦の画素が 181,649 から 240 へ落ちた。クリップは視線方向の深度で起きるので、深度で測る。

### 見えていた軌跡の大半は近接の拡大だった

終端処理を入れると平均濃さが 18.8 から 1.8 へ落ちた。翼端の深度は 23 m、1 区間は 254 m/s で 8.5 m なので、**カメラを追い越すまでが 3 点しかない。**その 7 m ぶんが至近距離で拡大され、画面の大半を占めていた。

つまり長い筋に見えていたものは、長い軌跡ではなく近接の拡大だった。終端したぶんは遠方の濃さで取り戻す。濃さの上限を 0.018 から 0.09 へ、半幅を 0.3 から 0.6 m へ。遠方で 1 画素を割らないようにする。結果は最大 22〜27 階調・断面 4〜12 階調。

### リボンの先頭はいまの翼端に繋ぐ

履歴は 4 ステップ（1/30 秒）ごとにしか記録しない。最新の点は最大で 1/30 秒ぶん後ろにあり、**翼端の目の前ではそれが数十画素の隙間になる。**同じ構図を再現すると、リボンの終わりが x=1070、翼端は x=1140。70 画素の隙間を実測した。

補間した現在の位置と姿勢から先頭の 1 点を作って足す。`AircraftSample` へ `wingtipVapor` を載せたので、濃さも現在の値で決まる。埋めたあとは x=1110 まで濃さ 26 階調が続き、そのまま主翼へ繋がる。

### 画面に映るのは 0.7 秒ぶんしかない

追従カメラは機体のすぐ後ろにいるので、軌跡はまたたく間にカメラの脇を過ぎて視錐台の外へ出る。

実測。`trailSegments` を変えて撮り比べると、**320 本と 48 本で画素が 1 ビットも違わない**。20 本まで落として初めて崩れ、左の渦が丸ごと消える。旋回でも同じで、bank-left の frame 1800 と 3000 で 192 本と 48 本の差は 0 画素。384 本と 192 本でも 0 画素。

**だから履歴を伸ばしても絵は伸びない。**「軌跡が短い」への答えは長さではなく、水蒸気の減衰だった。長さは 768 本（25.6 秒）まで持たせてあるが、これは途切れる原因を「履歴が尽きた」ではなく「画面の縁に達した」に固定するためと、後の Phase でカメラを増やすときの余裕。**画素が同じなら塗る量も同じ**なので、増える費用は頂点処理だけ。

## F-16 の取り込みで F/A-18C と違ったところ

1 機だけを見ていたときに仕様と取り違えていた前提が、3 つ崩れた。

### 1 枚の舵面が複数のオブジェクトに割れている

F/A-18C は `AileronLeft` が 1 オブジェクトだった。F-16 は上面と下面が別で（`LeftUpperAileron` と `LeftLowerAileron`）、ラダーは `Rudder.001`〜`Rudder.006` の 6 分割。だから機体の定義は `objects` で束ねる。

```js
{
  node: 'Rudder',                     // 出力する glb のノード名
  objects: ['Rudder.001', ..., 'VstabBandLeftAft', 'VstabBandRightAft'],
  from: [4.915, 0, 2.095],            // XML 座標
  axis: [0.547371, 0, 0.836890],
  maxDeg: 30, channel: 'rudder', sign: 1,
}
```

垂直尾翼の帯（塗装のデカール）も同じ回転に乗る。原典の rotate が挙げているので束ねた。

**束ねる相手は 1 つずつ検査する。**名前を打ち間違えると黙って `body` へ落ちて、舵が動かないまま見える。実際に `Rudder` という名のオブジェクトは原本に無かった（`F-16.xml` の rotate は挙げているが、この `.ac` には入っていない）。6 つのうち 5 つが当たるので、ノード単位の検査では通ってしまう。

### エルロンだけ rotate アニメーションが無い

この機体はエルロンとフラップをシェーダ側で回している。`effect` の `rotation-rad` にプロパティを、`rotation-x1`〜`rotation-z2` にヒンジの 2 点を渡す形。取り込んだ版ではエルロンの `effect` がコメントアウトされているが、座標そのものは残っている。

軸の方向は 2 点の差から出る。`(1.71989, −3.5817, 0.073898)` から `(1.3266, −1.0652, 0.170853)` へ。フラップの rotate が持つ軸 `(0.150157, −0.987872, −0.039515)` と符号だけ違う同じ直線で、突き合わせると一致する。

### 軸の向きが左右対称に置かれている

**ここが設計を変えた。**F/A-18C はエレベータの軸が左右で同じ向き（XML の `(0, 1, 0)`）だったので、同じ符号を与えれば一緒に動いた。F-16 は水平尾翼の軸が左右で逆を向いている（左 `(0, −0.981645, −0.190720)`、右 `(0, +0.981645, −0.190720)`）。同じ符号では差動尾翼になってピッチが効かない。

FlightGear 側も左右で別のプロパティを食わせて同じことをしている。左が `surface-positions/elevator-pos-norm`、右が `sim/multiplay/generic/float[4]`。

だから `src/render/aircraft/surfaces.ts` にあった「ノード名から指令と符号を引く表」を捨てた。舵面の名前、枚数、符号のどれもが機体で違う。機体の性質は機体の定義が持ち、glb の `extras.hinges` に `channel` と `sign` として載って描画側へ届く。

| 機体 | 舵面 | エルロンの軸 | エレベータの符号 | ラダー |
|---|---|---|---|---|
| F/A-18C | 6 枚 | 外向き（左 −X） | 左右とも −1 | 左右 2 枚 |
| F-16 | 5 枚 | 内向き（左 +X） | 左 +1 / 右 −1 | 1 枚 |

`tests/render/aircraftSurfaces.test.ts` が両機体で、後縁の点が上下どちらへ動くかを数値で固める。機体の定義から読むので、定義を直せば検査も付いてくる。

## 舵角の上限は FDM から取る

F/A-18C は `f18.xml` の rotate が `factor` で舵角を持っていた。F-16 の `F-16.xml` は水平尾翼に `factor 57.3` を持つが、これは正規化された −1..1 のプロパティに掛かる。そのまま読むと ±57.3 度で、実機の可動域とまったく合わない。

JSBSim の飛行制御が数値を持っている。`assets/upstream/f16/jsb-controls.xml` の `kinematic` の `clipto`。

| 舵面 | プロパティ | 上限 |
|---|---|---|
| 水平尾翼 | `fcs/fly-by-wire/pitch/horz-tail-{left,right}-deflection-deg` | ±25 度 |
| ラダー | `fcs/fly-by-wire/yaw/rudder-deflection-deg` | ±30 度 |
| フラッペロン | `fcs/fly-by-wire/roll/flaperon-{left,right}-deflection-deg` | −23..+20 度 |

水平尾翼の `description` には「defl. limit = 25, rate limit = 60 deg/s」とも書いてある。フラッペロンは上下で非対称だが、こちらは 1 つの上限しか持たないので狭い側の 20 度を採った。広い側を採ると下げ舵で舵面が翼から抜ける。

このファイルも原本としてコミットしてある。`tests/tools/ac3d.test.ts` が `clipto` を正規表現で読み、機体の定義の `maxDeg` と突き合わせる。**引き写した数字を自分で期待値に置くのではなく、原典から読んで比べる。**

## crease（稜線）を無視すると角が丸まる

AC3D は部品ごとに `crease <角度>` を持てる。面の法線どうしがこの角度より開いていたら、そこを稜線として扱って法線を平均しない。

F/A-18C の原本には `crease` 行が 1 つも無い。F-16 は 112 個の部品すべてに持っていて、値は 45 度から 179 度（大半は 80 度）。無視して部品内の全部を平均すると、90 度の角が丸まる。

実装は面ごとに平均する範囲を絞る形にした。

```js
function creasedNormal(adjacent, vi, flatNormal, cosCrease) {
  let x = 0, y = 0, z = 0
  for (const n of adjacent[vi]) {
    if (dot(n, flatNormal) < cosCrease) continue   // 稜線の向こう側は混ぜない
    x += n[0]; y += n[1]; z += n[2]
  }
  return normalize([x, y, z])
}
```

`crease` を持たない機体では `cosCrease` を `−Infinity` にする。全部混ざるので、以前とまったく同じ値になる。F/A-18C の glb のジオメトリ（BIN チャンク 993,916 バイト）が 1 バイトも変わらないことで確かめた。

同時に `data`（Blender のメッシュ名。長さ指定の生データ）と `texrep`（UV の繰り返し）にも対応した。`data` は**行数を決め打ちで飛ばしてはいけない。**改行を含むデータがあると、そこから先の解釈が全部ずれる。長さを見て飛ばす。`texrep` は両機体とも `1 1` しか出てこないので、それ以外は例外にした。黙って無視すると UV が崩れたまま気づけない。

## FlightGear が隠している部品を全部出すと絵が壊れる

原本を素直に全部描いたら、尾部に橙色の矩形が乗った。`chuteMat`（基本色 0.63/0.05/0.00）の 6 三角形で、`Chute` オブジェクト。

`F-16.xml` の `select` アニメーションを読むと、`Chute` は `RNLAF_Tailroot` と組で `sim/multiplay/generic/bool[36]` に掛かっている。オランダ空軍塗装の変種で、偽のときは `USAF_Tailroot` のほうが出る。**両方出ていた。**

同じ理由で隠すものが 21 個あった。全部 `select` の条件から拾ったもので、推測は入れていない。

| 隠すもの | 原典の条件 |
|---|---|
| `RNLAF_Tailroot` `Chute` | 塗装の変種。`bool[36]` |
| `GreenPosLight1` `RedPosLight1` `WingRedPosLight` `WingGreenPosLight` | 条件が `<property>false</property>`。出ることがない予備 |
| `LowFormationLlight` `FwdFormationLight` `AftPosLight1` `AftPosLight2` | マルチプレイの灯火フラグ |
| `Fan` | 停止中のファン。飛行中は `FanSpinning`。**両方 `.ac` の X が 0.58..0.60 で重なる** |
| `Turbine` | 条件が `<property>nop</property>`。未定義なので偽 |
| `LWStation1`〜`3` `RWStation1`〜`3` | 空のパイロン。搭載物があるときだけ |
| `Link16Antennas` `Tail-antenna` | 装備と型式の変種 |

これらは `stowed` という 1 つのノードにまとめる。`src/render/aircraft/model.ts` はこれを `gear` と一緒に隠す。捨てずに分けておく理由は、地上の場面を作るとき戻せるようにしておくため。

降着装置の扱いも変えた。既定の名前は `/Door|Gear|Wheel|Tire|Strut|Hook/i` だが、F-16 は脚が上がっているときに閉じる外扉を別オブジェクトで持っている。既定で拾うと腹に脚庫の穴が開き、`gearwellMat` の 169 三角形がそのまま見える。この機体では `Door` を外し、名前に `Gear` が入る `ExternalFrontGearDoor` だけ例外にした。

原本は 125 オブジェクト、18,042 三角形、10,627 頂点。ノードに分けたあとの数を測った。

| `stowed`（条件付きの部品） | 395 | 隠す |
| エルロン 2 枚 | 486 | 描く |
| 水平尾翼 2 枚 | 44 | 描く |

**空中で描くのは 15,554（86.2%）。**部品ごとに見ると、いちばん大きいのは前縁フラップの `LeftLowerLef` 3,872 と `RightLowerLef` 3,146 で、上面と合わせて 7,986 三角形（全体の 44%）。翼の前縁の薄い板にこれだけ使っている。次が主翼と胴体の一体メッシュ `RadarDomeTop` の 2,482。吸気口の中のファン（`FanR` ほか）が 1,087 あり、これは外からは見えない。

## テクスチャの変換で測ったこと

F-16 のテクスチャは PNG なのでブラウザが読める。それでも WebP へ落とした。`f16.png` が 2048×2048 の RGBA で 1.2 MB あり、そのまま配ると重い。品質 95 で 4 枚合計 1,756 KB が 436 KB になった。

劣化は sRGB の階調差で測る。**可視画素だけを数える。**

| ファイル | 大きさ | 原本 | WebP q95 | 可視部の RGB 平均差 | 最大 | アルファの差 |
|---|---|---|---|---|---|---|
| `f16.png` | 2048² RGBA | 1,220 KB | 243 KB | 0.54 階調 | 42 | 0 |
| `f16trans.png` | 512² RGBA | 36 KB | 18 KB | 0.63 階調 | 174 | 0 |
| `canopy2.png` | 512² RGBA | 500 KB | 175 KB | 1.72 階調 | 21 | 0 |
| `nozzle-ring.png` | 16² RGB | 133 B | 128 B | 0.33 階調 | 1 | 0 |

アルファは 3 枚とも最大差 0 で、1 階調も動かない。

**アルファが 0 の画素を含めて測ると読み違える。**`f16trans.png` は 74.8% が完全透明で、そこは RGB が任意の値を持っている。WebP の非可逆圧縮はそれを書き換えるので、分けずに測ると平均 16.3 階調・最大 255 になる。見えない画素の差なので数えない。この切り分けをしないと「劣化している」という結論が出る。

|---|---|---|---|---|

| 後処理だけ | 1.73 | −3.08 | 1.45 | −1.95 |
| 雲なし | 2.38 | −2.43 | 2.88 | −0.53 |
| 機体なし | 4.17 | −0.64 | 3.31 | −0.09 |
| 影なし | 4.30 | −0.51 | 3.38 | −0.02 |

環境反射はただ。時刻が変わったときだけ焼くので、毎フレームの費用がない。機体と影と軌跡を足しても 1.65 ms。Phase 3.5 で確かめた余裕の内側に収まる。

構図で費用の配分がまるで違う。高 G の構図は雲が 2.43 ms を占めるのに、低空の構図では 0.53 ms しかない。機体まわりも同じ。高 G では軌跡に 0.50 ms 掛かるが、低空では 0 になる。荷重倍数が 1.15 までしか行かず、渦が出ないため。

## E2E は並列で回す

基準画像 56 枚を SwiftShader で撮るので、直列だと 11.4 分かかっていた。同じファイルの中でも並列に走らせて 3.8 分になった。

**画素は変わらない。**キャプチャモードはフレーム番号だけから絵を決め、SwiftShader は CPU だけでラスタライズする。同時に何本走っていても結果は同じ。実測でも基準画像 16 枚が 1 枚も動かずに通った。

**詰め込みすぎると遅くなる。**Chromium 1 本がすでに複数スレッドで塗るので、コア数と同じ本数にすると取り合いになる。

| コア | ワーカー | 所要 |
|---|---|---|
| 8 | 1 | 11.4 分 |
| 8 | 4 | **3.8 分** |
| 8 | 8 | 4.7 分 |
| 4 | 2 | 6.1 分 |
| 4 | 3 | 5.8 分 |

コア数の半分にした。8 コアで 8 本は 4 本より 24% 遅い。GitHub の ubuntu-latest は 4 vCPU なので 2 本になる。

1 本あたりは遅くなる。最遅は 40.0 秒（8 コア 4 本）なので、1 テストの制限を 120 秒から 180 秒へ広げた。固まったときの検出は `e2e.yml` の段の上限が担う。

### ローカルの実測から CI を見積もると外れる

`taskset -c 0-3` で 4 コアに絞って測った 6.1 分に対し、CI の実測は **9 分 50 秒**だった。1.6 倍の乖離。`Running 56 tests using 2 workers` とログに出ているのでワーカー数は狙いどおりで、単にランナーが遅い。直列どうしの比（14 分 33 秒 対 11.4 分）で見ても 1.28 倍あり、残りは絞ったコアが L3 と帯域を丸ごと使える点の差。**コア数を絞っただけの模擬は楽観に出る。**

### 台数を増やすほうが効く

1 台のランナーは 4 vCPU しかないので、ワーカーを増やしても頭打ちになる。`--shard` で 2 台に分けると、それぞれ 28 件を 2 ワーカーで回す。GitHub Actions は matrix のジョブを並行に走らせるので、実時間は半分に近づく。

## 描かれていないことをどう見つけるか

影を入れたときに地形が丸ごと消えた。原因にたどり着くまでに使った道具を残しておく。

`renderer.info` の `calls` と `triangles` を `TestHook` に出した。ただし `renderer.info` は `renderer.render()` ごとに 0 へ戻る。そのままでは最後のポストパスだけが残り、「ドローコール 1」に見える。`autoReset = false` にしてフレームの頭で消す。これで「地形は 438k 三角形ぶん投入されている」と分かり、**描かれていないのではなく描いた結果が捨てられている**と切り分けられた。

`git stash` で作業中の変更を外して撮り直し、基準画像と画素単位で比べた。HEAD では一致し、作業中では一致しない。ここで原因が作業中の変更にあると確定した。

**GL のエラーは Chrome のコンソールに `warning` として出る。**`error` だけを拾っていたので取りこぼしていた。`gl.getError()` を直接呼んで 1282 を得て、そこからコンソールの警告を洗い直した。計測スクリプトは `warning` も拾うようにしてある。

## 検算の考え方

自分のパーサが出した数値を自分で期待値に置くと、回帰しか防げない。正しさは外の事実と突き合わせて確かめる。使える外の事実が 3 つあった。

原本を素の正規表現で数えた値（201 オブジェクト、12,260 頂点、18,634 三角形、9,866 サーフェス）。FlightGear のアニメーション XML が持つヒンジの座標。実機の F/A-18C の寸法。

この 3 つをテストに書いてある。パーサを書き換えても、座標系を取り違えたり `loc` を落としたりすれば必ず落ちる。
