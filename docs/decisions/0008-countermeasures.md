# 0008 ミサイル警告とフレア

2026-08-25 決定。Phase 6.5。

原理と実装の対応は `docs/weapons.md`、HUD の表示は `docs/hud.md` にある。ここには判断とその根拠だけを残す。

## 決めたこと

シーカーが掴む熱源を熱の強さと距離で選ぶ。掴む先と殴る先を分ける。ミサイル警告は方位を出す。敵にもフレアを持たせる。台本ごとにミサイルとフレアの数を選べるようにする。

## 幾何だけでは囮が効かない

着手時の設計は「シーカーが視野内の熱源のうち視線角の小さいものを追う」だった。位置関係だけで決まるので決定論で検証でき、どの角度なら効くかを説明できる。ユーザーにもこの方針で確認を取った。

**実測で崩れた。**ミサイルが機体を正確に追っている限り、機体への視線角は 0.00 度になる。軸から外れるフレアに勝ち目がない。真後ろ 1,500 m から撃たれて 1.0 秒でフレアを撒き、4.8 秒のあいだ一度も掴まなかった。フレアの視線角は 0.04 度から 174 度へ離れる一方だった。

実機のフレアが騙せるのは、機体の排気よりはるかに明るいから。マグネシウム系の火工品は 2,000 K 前後まで上がるとされ、タービン排気の 700〜900 K より高い。放射は温度の 4 乗に比例するので、面積が小さくても総量で勝つ。熱の強さが本質的な要素だった。

スコアをこう置いた。

```
score = intensity / range² / (1 + (視線角 / 角度分解)²)
```

距離の逆二乗も要る。落とすと、正面から来るミサイルに対して機体の向こう側へ落ちたフレアが勝ってしまう。近いほど強く見えるのが物理として正しい。

確率は使っていない。同じシードと同じ入力からは同じ結果になる。ユーザーが選んだ「決定論で検証できる」という条件は守れている。

## 掴む先と殴る先を分ける

`Missile.tracked` にシーカーが掴んでいる熱源を持たせ、近接信管もそれに対して判定する。囮を掴んでいれば囮の近くで爆発し、本来の標的は無傷。

混ぜると「フレアを出したのに落ちる」という壊れ方をする。`Combat` 側も `missile.tracked !== player` でダメージを飛ばす。

型も分けた。`HeatSource`（位置・速度・生死・強さ）が `Tracked`（さらに姿勢と対気速度）の下にある。フレアには姿勢がなく、対気速度も持たない。シーカーから見て機体と区別が付かない。それが囮の成立する理由なので、型でもそう表す。

姿勢を持たない熱源への信管は球で判定する。カプセルは機体座標に置いてあるので姿勢が要るが、フレアには向きがない。無回転を渡すと機体の形で判定してしまう。

## 警告に方位を出す

有無だけでは、どちらへ逃げるか決められない。輪の上の三角を方位ぶん回す形にした。

接近しているものだけ数える。外れたあとも鳴り続けると意味が薄れる。フレアで逸らしたミサイルは離れていくので、そこで消える。それが「振り切った」の手応えになる。

## 敵にもフレアを持たせる

着手時は「持たせない」と決めていた。自機の防御が成立すればチェックポイントとして十分で、敵の投下判断は AI の状態を増やすことになるからだった。

**覆した。理由は絵の見張りが作れないこと。**追従カメラは自機の後方 23 m から前を向く。フレアは自機の後ろへ落ちるので、撒いた 0.7 秒後には前方深度が −23.7 m でカメラの後ろにいる。旋回してもバンク −104 度まで倒して視線角 155〜173 度のままだった。**後ろへ落ちるものは原理的に画角へ入らない。**

前方 220 m の敵が撒く絵なら正面に写る。実測で 1,605 画素・最大 63 階調。

AI の状態は増やさなかった。撒くのは回避へ入った瞬間。後ろにつかれている状態なので、ミサイルが来ていてもおかしくない。ミサイルを見てから判断させると、脅威の検出を AI が持つことになる。

## 台本ごとに数を選べるようにする

`EnemySpec` に `missiles` と `flares` を足した。0 を渡せばそれぞれ持たない敵になる。

混ざると絵が読めない。`enemy-attack` は機銃で撃たれる絵の見張り。ミサイルを持たせると 5.2 秒で自機が落ち、曳光弾が 1 発も出ないまま絵が変わった（`exact.mjs` が差分 46.1% で捕まえた）。`damage-smoke` は敵が回避に入ってフレアを撒き、1,250 画素動いた。

「その台本が何を見るためのものか」を明示する形になった。

## 強度は駆け引きから決めた

2 から 32 まで 6 段階に振った。6 以上は飽和してどの方向でも効く。4 を選んだ。

| 撃たれた方向 | なし | 0.5s | 1.0s | 1.5s | 2.0s |
|---|---|---|---|---|---|
| 180 度（真後ろ） | 命中 | 囮 | 囮 | 囮 | 囮 |
| 135 度 | 命中 | 命中 | 命中 | 外れ | 外れ |
| 90 度 | 命中 | 命中 | 命中 | 命中 | 命中 |
| 0 度（正面） | 命中 | 命中 | 命中 | 命中 | 囮 |

**真後ろにつかれたらフレアで振り切れるが、横からは旋回で逃げるしかない。**

## 実測で外れた前提

**「正面では効かない」は構図として成立しなかった。**正面同士だとすれ違いが速すぎて、フレア以前にミサイルが当たらない。敵は 1 発撃ったあと機銃の間合いへ入り、自機は無傷のままだった。横 90 度に変えて成立させた。

至近のビルボードは画角いっぱいに広がる。半径 1.6 m の板が画面の下半分を白く塗りつぶした（76,401 画素・最大 148 階調）。`clampRadiusToNear` は near 面を跨がないよう絞るだけで、これは止められない。カメラから 20 m で切った。

暈の正体は煙だった。火の濃さを 0.9 から 0.35 へ下げても白い暈が消えず、煙を 0.35 から 0.12 へ薄くして初めて締まった。煙の半径は火の 2 倍あるので、外側の白はほぼ煙。

near 面の断面は出ていない。最接近 25.9 m のフレームで測って輪郭 342 画素・12 階調以上 0 画素・最悪 8 階調。拡大しても切り口はなかった。

## フレアを赤くする作業は持ち越した（2026-08-28）

爆発を赤い燃焼へ直したとき、フレアにも同じ設計を当てようとして止めた。**原因が突き止められていない状態で基準画像を動かしたくないため。**

加算合成では赤が出ないところまでは同じで、理由も同じ（`docs/weapons.md` の「加算合成では赤が出ない」）。フレアの火を通常合成へ変え、比を爆発と揃え、不透明度を上げても、出力は彩度 9〜20 のピンクにしかならなかった。

途中で見つけたものを 2 つ残す。

`renderOrder` を指定していない。three は透明を `renderOrder → z 降順 → id 昇順` で並べ替える（`WebGLRenderLists.js` の `reversePainterSortStable`）。火と煙は同じ位置に置くので z が一致し、`fire` を先に生成しているぶん火が先に描かれる。**コメントの「煙を先に描く。火が上に乗る」は実際と逆で、煙が上に乗っていた。**加算だった頃は順序が結果を変えないので露出しなかった。

火の不透明度が線形に薄れる。`fade = ignition * remaining` なので、燃焼 4 秒のあいだ半透明のまま煙と混ざる。実測で経過 1.49 秒に 0.596。**爆発の芯で直したのと同じ欠陥**（`sim/effects.ts` の `coreOpacity` は保持してから落とす）。

**残っているのは背景による非対称。**同じ円・同じ指令 0.95 で、実効の不透明度が空を背景に 0.129、山を背景に 0.794 になる。6 倍の差が「後ろに何があるか」で決まる。

**バイト値の差で比べてはいけない。**AgX は明部を圧縮するので、同じ線形の変化が明るい背景では小さい階調差になる。一度これで誤読した（最大差 92 対 7 を見て「大きさに依存する」と読んだが、線形へ戻すと大きさには依存していなかった）。画素ごとに線形へ戻して実効不透明度を出す `alpha.mjs` を書いた。

合成そのものは厳密に正しい。半径 6 m で実効 0.535 / 0.553 / 0.546（指令 0.55）、半径 20 m で 0.797 は 2 枚が重なった値 1 − 0.45² = 0.798 と一致する。値も材質まで正しく届く（診断で `alpha=0.950` `r=1.600`）。円は 18 画素の完全な平坦で、ぼけていない。

**深度バッファが持ち主を決めている。**フレアの材質に `depthWrite = true` を入れると、空を背景にした実効が 0.129 から 0.985 へ跳ね、画素が `rgb(3,14,31)` の黒になる。

**それでも爆発は説明が付かない。**爆発も `depthWrite: false` で、標的・曳光弾・自機・ダメージの煙を全部消して空だけを背景にしても実効 0.821 のまま。フレアだけが 0.129 になる。

責任のあるコードまでは辿った。`node_modules/@takram/three-atmosphere/src/shaders/aerialPerspectiveEffect.frag:297` の遠平面の分岐。

```glsl
float depth = readDepthValue(depthBuffer, uv);
if (depth >= 1.0 - 1e-8) {
  #ifdef SKY
  outputColor.rgb = getSkyRadiance(...);   // inputColor を捨てる
  #else
  outputColor = inputColor;
  #endif
  #ifdef HAS_OVERLAY
  outputColor.rgb = outputColor.rgb * (1.0 - overlay.a) + overlay.rgb;
  #endif
  return;
}
```

`sky` の既定は false で、この案件も有効化していない。だから色は保存され、そのあと雲の overlay が合成される。

**雲の overlay は無実だった。**`scene.ts` の `setOverlay(null)` で外して測っても平坦値は 0.129 のまま動かない。

**色によって振る舞いが変わる。**同じ円・同じ指令 0.95・`falloff` 0 で、色だけを替えて中心の生の画素を読んだ（参照は `rgb(159,175,194)`）。

| 火の色 | 実測 | 通常合成の予測 | 加算合成の予測 |
|---|---|---|---|
| 黒 `(0,0,0)` | `rgb(151,169,190)` | 暗い（0.05 倍） | 変化なし |
| 白 `(1,1,1)` | `rgb(241,237,229)` | `rgb(244,244,244)` | ほぼ白 |
| 緑 `(0,0.5,0)` | `rgb(185,224,193)` | `rgb(187,233,160)` | `rgb(202,236,201)` |

**どちらの合成でも説明が付かない。**白は通常合成の予測と合う。黒は通常合成なら暗くなるはずが 8 階調しか動かない。緑は R が通常合成寄り（185 対 187）で B が加算寄り（193 対 201）。

一方で爆発は通常合成として素直に振る舞う。同じ空を背景に（水平線は y=380〜390、爆発の芯は y=326）G を 201 → 126、B を 206 → 105 まで下げている。

除外できたものを残す。雲の overlay。ビルボードの大きさ（線形で測れば依存しない）。`sky.renderOrder = 1000`（`SkyMaterial` は不透明なので透明キューより前）。フレアの描画元が二重にあること（`createFlares` は 1 か所）。`place()` の値（診断で `alpha=0.950` `r=1.600`）。

**次に見るのは実際の GL の状態。**材質は `NormalBlending` と書いてあるのに黒が効かない。`renderer.getContext()` から blend func を直接読む。あわせて `WebGLRenderer` の `premultipliedAlpha` と HalfFloat の描画先でのアルファの扱いを当たる。爆発との差はそこを見ないと詰められない。

**`sky.renderOrder = 1000` は上書きの犯人ではない。**`SkyMaterial` は不透明なので、three は不透明キューを全部描いてから透明キューに入る。renderOrder はキューの内部の順序しか決めないので、空の板は透明のビルボードより前に描かれる。コメントの「不透明ジオメトリのあとに描く」がこの誤読を招きやすい。

減衰と最大差の実測（`enemy-flare` f180、黒・不透明度 0.95・煙なし、`?flares=0` との引き算）。

| 減衰 | 画素 | 最大差 |
|---|---|---|
| 0.0 | 458 | 92 |
| 0.3 | 455 | 44 |
| 0.6 | 399 | 28 |
| 1.0 | 301 | 16 |
| 1.8 | 177 | 7 |

不透明度は材質まで正しく届いている（診断を仕込んで `alpha=0.950` `r=1.600` を確認）。円の大きさも約 17 画素で幾何どおり。
