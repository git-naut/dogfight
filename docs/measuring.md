# 実機での計測

WSL からは実機の GPU 性能を測れない。Chromium が Intel Arc を掴まず llvmpipe（CPU ラスタライザ）に落ちるので、出てくる数字は別のものになる。**実機の値は Windows 側の Chrome で読む。**

このファイルは手順の控え。これまでに踏んだ計測の罠も、同じ場所にまとめてある。

## 手順

WSL 側でプレビューサーバを上げる。

```bash
cd /mnt/c/Users/naut8/dev/dogfight
npm run build && npm run preview -- --port 4173 --strictPort --host 0.0.0.0
```

`--host 0.0.0.0` を明示する。既定では WSL の中からしか届かない。

Windows 側の Chrome で開く。WSL2 の IP は `hostname -I` で確認する（`localhost` で届くこともあるが、届かなければ IP を使う）。

```
http://<WSL の IP>:4173/dogfight/?debug=1
```

## 2 つの読み方

ライブループの `?debug=1` では、実際に遊ぶ状態の値が読める。判断は GPU 時間の「最大」で行う。現在値は結果が揃ったときにしか更新されない。重いフレームほど古い軽い値が残る。「GPU 10.8 ms なのに FPS 46」を見て CPU に 11 ms あると読み違えたことがある（Phase 3）。実際の CPU は 0.7 ms だった。

`?sweep=1` は描画の要素を 1 つずつ切って差を測る。1 枚を何度も描くので絶対値はライブループより速く出る。GPU のクロックが上がりきった状態になり、中央値と 3 倍開く。**確定できるのは配分で、絶対値はライブループで読む。**

```
http://<IP>:4173/dogfight/?capture=1&sweep=1&script=weapons-load&frame=240&nodegrade=1
```

`?nodegrade=1` を忘れない。プリセットをまたぐと `maxPixelRatio` も変わる（high 2 / medium 1.5）ので、固定しないと GPU 時間を比較できない。

## 台本を選ぶ

武装を測るなら `weapons-load` を使う。**武装がすべて同時に出ている構図でないと測れない。**標的 2 機・機銃が飛んでいる・ミサイルの煙が伸びている・爆発が出ている、を 1 フレームに揃えてある。実測で f200 以降なら全部出る（f240 なら弾 80 発・煙 30 点・爆発 1 個）。

**どれか 1 つでも出ていないと、その列の差が 0 になる。**0 が出たときに「費用が無視できる」なのか「そもそも描かれていない」なのか区別が付かなくなる。

敵機を測るなら `enemy-eight` を使う。8 機が同時に出ている構図で、実測で三角形が 470,521 から 599,033 へ増え、ドローコールが 85 から 413 へ増える。

**表の見出しに測定条件が出る。**台本、フレーム、時刻、雲量、プリセット、画素数、敵機と標的の数。絵だけを見て何を測ったか確かめられる。

```
台本 enemy-eight / f240 / 16.0 時 / 雲量 0.30 / preset high / 劣化なし / 1280 x 720 画素 / 敵機 8 機 / 標的 0 機
```

画素数が入っているのは、GPU 時間が画素数にほぼ比例するから。**窓の大きさが違う 2 回の計測は比べられない。**

構図は 1 つで判断しない。海の上と稜線の上では費用の配分がまるで違う（Phase 3.5 の実測）。`low-pass`（低空）と `pull-up`（高 G）も併せて測る。

## 表の読み方

`?sweep=1` の表には 8 列ある。読む順番がある。

**まず「三角形（総数）」を見る。**切った条件で値が動いていなければ、そもそも切れていない。**実際にこれで 1 度騙された。**以前は地形の三角形だけを記録していたので、機体や武装を切っても全条件が同じ数のまま並び、「費用が無視できる」のか「描かれていない」のか区別が付かなかった。

**次に「判定」を見る。**差がばらつきの内側なら「誤差以下」、符号が逆（切ったのに遅い）なら「逆（+N）」と出る。ばらつきの目安は表の下に実測値が出ている（最小値と中央値の差の中央値）。

**「逆」が並んでいたら計測が成立していない。**切ったほうが遅くなるのは物理的にありえない。前回の実機の計測で武装の差が +0.01〜+0.13 ms とすべて正の値で並び、それで気づいた。

**「有意」だけを内訳として読む。**

**GPU の列だけでは足りない条件がある。**この機体構成では GPU は三角形にほとんど反応しない。実測で、地形を切って三角形が 474k から 36k へ 92% 減っても GPU 時間は 0.77 ms（12%）しか減らなかった。Phase 3.5 の実測（地形の三角形を 44% 減らして 0.03〜0.05 ms）と同じ傾向。

**ドローコールが増える条件は CPU の列で読む。**敵 8 機で増えるのはドローコール（85 → 413）で、これは投入側の費用なので CPU 時間に出る。三角形は 26% 増えるが、上の感度から GPU への影響は 0.2 ms 程度と見込まれる。

## 引き算で測るときの作法

遮蔽物を切ると裏のものが代わりに描かれる。海面を切ると隠れていた空のクアッドが描かれ、空の散乱シェーダは海面より高いので逆に遅くなる。「後処理だけ」の床を必ず併せて測る。

**代表値は最小値。**割り込みは時間を増やす方向にしか効かない。平均と中央値は環境の騒がしさを拾う。最小値に替えて初めて部分の和が全体と合った。

1 周ごとに開始位置をずらす。設定ごとにまとめて測ると後半ほど遅く出る。総当たりにしても 1 周内の位置が結果に乗る（法線摂動なしが基準より 228 ms 遅いという値が出た）。`bench.ts` はこれを済ませてある。

サンプル数の比から ms を外挿しない。雲で +31% と見積もって実際は +58% だった。

## 切ったまま戻らない条件があった（2026-08-24 決着）

`?sweep=1` を実機で 2 回回して、どちらも三角形の総数が全行 474k で並んだ。「敵機なし」の行も基準と同じ。

**`runBenchSweep` の `base` に `enemies` が入っていなかった。**`setMeasureConfig` は `undefined` の項目を触らない。一度「敵機なし」を通ると二度と戻らない。順番は 1 周ごとにずらすので、最初の周で通った時点から全条件が敵機なしで測られる。三角形は最後の周の値だけが残り、全行で同じ数になる。

**三角形の列でも見分けられなかった。**`enemy-eight` から敵 8 機を消すと 599,033 − 8 × 16,184 ≒ 469,561。`level` の 470,521 とほぼ同じで、どちらも 474k と表示される。だから「台本を渡し忘れた」と読み違えた。

埋め忘れを型で止めた。`MeasureToggles` は `MeasureConfig` の真偽値の項目をすべて必須にする型で、`base` の型をこれにすると 1 つでも書き忘れた時点で `tsc` が落ちる。実際に `enemies` と `damageSmoke` の 2 つを名指しで捕まえた。

直したあとの実測（SwiftShader / 1280 x 720 / `enemy-eight` f240）。**GPU 時間は SwiftShader なので読まない。三角形だけを見る。**

| 条件 | 三角形 | 基準との差 |
|---|---|---|
| 基準 | 599k | — |
| 敵機なし | 474k | −125k |
| ダメージの煙なし | 595k | −4k |
| 機体なし | 567k | −32k |
| 地形なし | 161k | −438k |

**引き算で測るときは、切ったものが減ったことを別の数字で確かめる。**この規則は前から書いてあったが、確かめる側の数字（三角形の総数）まで同じ欠陥に巻き込まれていた。

## 全条件を回すと機械が熱で遅くなる（2026-08-24 実測）

同じ機械（Intel Arc 140V / preset high / `enemy-eight` f240）で 4 回測った。**試料を増やすほど基準そのものが遅くなり、ばらつきも増えた。**

| 回 | 基準の GPU 最小 | ばらつき | 敵機なしの差 | 判定 |
|---|---|---|---|---|
| 1 | 6.14 ms | 0.35 ms | 未計測 | — |
| 2 | 11.67 ms | 0.94 ms | 未計測 | — |
| 3 | 7.01 ms | 3.84 ms | −1.09 ms | 誤差以下 |
| 4 | 16.22 ms | 6.01 ms | −2.05 ms | 誤差以下 |

4 回目は「雲なし」−7.30 ms と「後処理だけ」−9.00 ms が有意に出たので、表の警告は出ない。**それでも敵機の費用は測れていない。**−2.05 ms がばらつき 6.01 ms の内側。CPU の列でも +1.10 ms で、符号が逆。

21 条件 × 試料 N 回 × 2 描画。統合 GPU は CPU と電力枠を分け合うので、これを続けると熱で動作周波数が落ちる。**試料を増やす助言は裏目に出た。**

だから条件を絞れるようにした。`?only=base,enemies` のように ascii 名で選ぶ。基準は選ばなくても入る（差の基準になる）。知らない名前だけで基準しか残らないときは全条件へ戻す。1 行の表を出しても何も分からないので。

```
?capture=1&sweep=1&script=enemy-eight&frame=240&nodegrade=1&hour=16&only=enemies&bench=200
```

2 条件なら総量が 10 分の 1 になる。試料を増やしても熱が乗らない。見出しに「2 条件 x 試料 200 回」と出る。

### 雲を切った上で比べる

**雲は GPU 時間の最大項で、ばらつきの主因でもある。**実機で 5.97〜9.00 ms。敵機の差はどの回もばらつきの内側だった（−1.09 / −2.05 ms 対 ばらつき 3.84 / 6.01 ms）。

そこで「雲なし」と「雲なし＋敵機なし」を並べる条件を用意した。

```
?capture=1&sweep=1&script=enemy-eight&frame=240&nodegrade=1&hour=16&only=clouds,cloudsenemies&bench=200
```

**敵機の費用は「雲なし」と「雲なし＋敵機なし」の引き算で取る。**表の差の列は基準との差なので、そこは手で引く。三角形が 599k と 474k に分かれていれば、切れていることは確かめられる。

雲を足した状態の合計は、この差を「雲あり」の基準に足して見積もる。GPU が直列に律速している限りは加算で足りる。**それでも遊べるかどうかはライブループで見る。**

**60 fps が出るかは sweep では判定しない。**sweep は vsync を待たずに描き続けるので、遊んでいるときより負荷の掛け方が重い。`?debug=1` のライブループが GPU 時間と最大を 16.7 ms と並べて出すので、そちらで見る。

## 「有意」が 1 つも無い表は読めない（2026-08-24 実測）

欠陥を直したあと、実機で 3 度目を回した。**構造は正しくなった。**見出しは「敵機 8 機」、三角形は基準 599k・敵機なし 474k で分かれる。全条件が実際に切れている。

それでも読めなかった。ばらつきの目安 3.84 ms に対して、いちばん大きい差が後処理だけの −2.24 ms。**「有意」の行が 1 つも無い。**

| 条件 | GPU 最小 | 基準との差 | 三角形 |
|---|---|---|---|
| 基準 | 7.01 ms | — | 599k |
| 後処理だけ | 4.77 ms | −2.24 ms | 161k |
| 雲なし | 5.14 ms | −1.87 ms | 599k |
| 敵機なし | 5.93 ms | −1.09 ms | 474k |
| lod 0.65 | 9.21 ms | +2.20 ms | 476k |

**費用が無いのではなく測れていない。**後処理の連鎖は別の回に 2.75〜3.39 ms と出ている。

CPU の列も同じ。「敵機なし」は −2.30 ms。CPU をほとんど減らさないはずの「海面なし」が −2.20、「環境反射なし」が −1.90、`cells 24` が −1.90 で並ぶ。`lod 0.65` は +2.30。分離できない。

**騒がしさは GPU 中央と最小の差に出る。**基準は 7.01 と 11.30 で 4.29 ms 開いている。3 回のばらつきは 0.35 → 0.94 → 3.84 ms。同じ機械なので、環境が違う。

表が自分で言うようにした。「有意」が 1 つも無いときは警告を出す。全行を突き合わせないと気づけない条件なので、人が読む前の段階で表に判定させる。

判定は `bench.ts` の純関数（`benchNoiseFloor` / `benchBestGain` / `benchUnreadable`）。表の判定列と警告で同じ値を使う。別々に書くと食い違う。

**発火は絵では確かめられない。**SwiftShader は騒がしいが、後処理の差が桁で出る（実測でばらつき 493.29 ms・後処理だけ −513.39 ms）。だから「読める」と判定されて警告が出ない。`tests/render/benchVerdict.test.ts` が実機の 21 行をそのまま入れて発火を固定する。**部分集合では中央値が合わない**（6 行に削ったら 3.80 になった）。

測り直すときは、ほかの負荷を止め、電源につないで、`?bench=120` のように試料を増やす（既定は 40）。見出しに試料の数が出る。

## 計器が嘘をついた例

キャプチャモードは DPR を 1 に固定している。基準画像を機械に依らせないため。実機は DPR 1.50 で画素数が 2.25 倍あるので、計測モード（`?sweep=1`）だけ実 DPR を使う。

タイマークエリの結果は同じ JavaScript タスクの中では揃わない。`gl.finish()` のあと 10 万回ポーリングしても `QUERY_RESULT_AVAILABLE` が立たない。`requestAnimationFrame` をまたいで回収する。

`gl.finish()` では Chrome の描画は同期しない。`gl.readPixels` で読み戻さないと投入時間しか測れない。全解像度が 1/4 より速いという嘘の値が出た。

## 判断の基準

GPU の最大が 16.7 ms を超えるなら、プリセットの列を下げる。下げる先は実測で決める。**推定で下げない。**「16bit にすると帯域が倍で重くなる」と見込んだことがある。実測では 16bit のほうを速く測った（Phase 3）。
