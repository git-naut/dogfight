# 実機での計測

WSL からは実機の GPU 性能を測れない。Chromium が Intel Arc を掴まず llvmpipe（CPU ラスタライザ）に落ちるので、出てくる数字は別のものになる。**実機の値は Windows 側の Chrome で読む。**

このファイルは手順の控え。これまでに踏んだ計測の罠も、同じ場所にまとめてある。

## 手順

WSL 側でプレビューサーバを上げる。

```bash
cd /mnt/c/Users/naut8/dev/dogfight
npm run build && npm run preview -- --port 4173 --strictPort --host 0.0.0.0
```

`--host 0.0.0.0` を明示する。既定では WSL の中からしか届かない。

Windows 側の Chrome で開く。WSL2 の IP は `hostname -I` で確認する（`localhost` で届くこともあるが、届かなければ IP を使う）。

```
http://<WSL の IP>:4173/dogfight/?debug=1
```

## 2 つの読み方

ライブループの `?debug=1` では、実際に遊ぶ状態の値が読める。判断は GPU 時間の「最大」で行う。現在値は結果が揃ったときにしか更新されない。重いフレームほど古い軽い値が残る。「GPU 10.8 ms なのに FPS 46」を見て CPU に 11 ms あると読み違えたことがある（Phase 3）。実際の CPU は 0.7 ms だった。

`?sweep=1` は描画の要素を 1 つずつ切って差を測る。1 枚を何度も描くので絶対値はライブループより速く出る。GPU のクロックが上がりきった状態になり、中央値と 3 倍開く。**確定できるのは配分で、絶対値はライブループで読む。**

```
http://<IP>:4173/dogfight/?capture=1&sweep=1&script=weapons-load&frame=240&nodegrade=1
```

`?nodegrade=1` を忘れない。プリセットをまたぐと `maxPixelRatio` も変わる（high 2 / medium 1.5）ので、固定しないと GPU 時間を比較できない。

## 台本を選ぶ

武装を測るなら `weapons-load` を使う。**武装がすべて同時に出ている構図でないと測れない。**標的 2 機・機銃が飛んでいる・ミサイルの煙が伸びている・爆発が出ている、を 1 フレームに揃えてある。実測で f200 以降なら全部出る（f240 なら弾 80 発・煙 30 点・爆発 1 個）。

**どれか 1 つでも出ていないと、その列の差が 0 になる。**0 が出たときに「費用が無視できる」なのか「そもそも描かれていない」なのか区別が付かなくなる。

敵機を測るなら `enemy-eight` を使う。8 機が同時に出ている構図で、実測で三角形が 470,521 から 599,033 へ増え、ドローコールが 85 から 413 へ増える。

**表の見出しに測定条件が出る。**台本、フレーム、時刻、雲量、プリセット、画素数、敵機と標的の数。絵だけを見て何を測ったか確かめられる。

```
台本 enemy-eight / f240 / 16.0 時 / 雲量 0.30 / preset high / 劣化なし / 1280 x 720 画素 / 敵機 8 機 / 標的 0 機
```

画素数が入っているのは、GPU 時間が画素数にほぼ比例するから。**窓の大きさが違う 2 回の計測は比べられない。**

構図は 1 つで判断しない。海の上と稜線の上では費用の配分がまるで違う（Phase 3.5 の実測）。`low-pass`（低空）と `pull-up`（高 G）も併せて測る。

## 表の読み方

`?sweep=1` の表には 8 列ある。読む順番がある。

**まず「三角形（総数）」を見る。**切った条件で値が動いていなければ、そもそも切れていない。**実際にこれで 1 度騙された。**以前は地形の三角形だけを記録していたので、機体や武装を切っても全条件が同じ数のまま並び、「費用が無視できる」のか「描かれていない」のか区別が付かなかった。

**次に「判定」を見る。**差がばらつきの内側なら「誤差以下」、符号が逆（切ったのに遅い）なら「逆（+N）」と出る。ばらつきの目安は表の下に実測値が出ている（最小値と中央値の差の中央値）。

**「逆」が並んでいたら計測が成立していない。**切ったほうが遅くなるのは物理的にありえない。前回の実機の計測で武装の差が +0.01〜+0.13 ms とすべて正の値で並び、それで気づいた。

**「有意」だけを内訳として読む。**

**GPU の列だけでは足りない条件がある。**この機体構成では GPU は三角形にほとんど反応しない。実測で、地形を切って三角形が 474k から 36k へ 92% 減っても GPU 時間は 0.77 ms（12%）しか減らなかった。Phase 3.5 の実測（地形の三角形を 44% 減らして 0.03〜0.05 ms）と同じ傾向。

**ドローコールが増える条件は CPU の列で読む。**敵 8 機で増えるのはドローコール（85 → 413）で、これは投入側の費用なので CPU 時間に出る。三角形は 26% 増えるが、上の感度から GPU への影響は 0.2 ms 程度と見込まれる。

## 引き算で測るときの作法

遮蔽物を切ると裏のものが代わりに描かれる。海面を切ると隠れていた空のクアッドが描かれ、空の散乱シェーダは海面より高いので逆に遅くなる。「後処理だけ」の床を必ず併せて測る。

**代表値は最小値。**割り込みは時間を増やす方向にしか効かない。平均と中央値は環境の騒がしさを拾う。最小値に替えて初めて部分の和が全体と合った。

1 周ごとに開始位置をずらす。設定ごとにまとめて測ると後半ほど遅く出る。総当たりにしても 1 周内の位置が結果に乗る（法線摂動なしが基準より 228 ms 遅いという値が出た）。`bench.ts` はこれを済ませてある。

サンプル数の比から ms を外挿しない。雲で +31% と見積もって実際は +58% だった。

## 切ったまま戻らない条件があった（2026-08-24 決着）

`?sweep=1` を実機で 2 回回して、どちらも三角形の総数が全行 474k で並んだ。「敵機なし」の行も基準と同じ。

**`runBenchSweep` の `base` に `enemies` が入っていなかった。**`setMeasureConfig` は `undefined` の項目を触らない。一度「敵機なし」を通ると二度と戻らない。順番は 1 周ごとにずらすので、最初の周で通った時点から全条件が敵機なしで測られる。三角形は最後の周の値だけが残り、全行で同じ数になる。

**三角形の列でも見分けられなかった。**`enemy-eight` から敵 8 機を消すと 599,033 − 8 × 16,184 ≒ 469,561。`level` の 470,521 とほぼ同じで、どちらも 474k と表示される。だから「台本を渡し忘れた」と読み違えた。

埋め忘れを型で止めた。`MeasureToggles` は `MeasureConfig` の真偽値の項目をすべて必須にする型で、`base` の型をこれにすると 1 つでも書き忘れた時点で `tsc` が落ちる。実際に `enemies` と `damageSmoke` の 2 つを名指しで捕まえた。

直したあとの実測（SwiftShader / 1280 x 720 / `enemy-eight` f240）。**GPU 時間は SwiftShader なので読まない。三角形だけを見る。**

| 条件 | 三角形 | 基準との差 |
|---|---|---|
| 基準 | 599k | — |
| 敵機なし | 474k | −125k |
| ダメージの煙なし | 595k | −4k |
| 機体なし | 567k | −32k |
| 地形なし | 161k | −438k |

**引き算で測るときは、切ったものが減ったことを別の数字で確かめる。**この規則は前から書いてあったが、確かめる側の数字（三角形の総数）まで同じ欠陥に巻き込まれていた。

## 全条件を回すと機械が熱で遅くなる（2026-08-24 実測）

同じ機械（Intel Arc 140V / preset high / `enemy-eight` f240）で 4 回測った。**試料を増やすほど基準そのものが遅くなり、ばらつきも増えた。**

| 回 | 基準の GPU 最小 | ばらつき | 敵機なしの差 | 判定 |
|---|---|---|---|---|
| 1 | 6.14 ms | 0.35 ms | 未計測 | — |
| 2 | 11.67 ms | 0.94 ms | 未計測 | — |
| 3 | 7.01 ms | 3.84 ms | −1.09 ms | 誤差以下 |
| 4 | 16.22 ms | 6.01 ms | −2.05 ms | 誤差以下 |

4 回目は「雲なし」−7.30 ms と「後処理だけ」−9.00 ms が有意に出たので、表の警告は出ない。**それでも敵機の費用は測れていない。**−2.05 ms がばらつき 6.01 ms の内側。CPU の列でも +1.10 ms で、符号が逆。

21 条件 × 試料 N 回 × 2 描画。統合 GPU は CPU と電力枠を分け合うので、これを続けると熱で動作周波数が落ちる。**試料を増やす助言は裏目に出た。**

だから条件を絞れるようにした。`?only=base,enemies` のように ascii 名で選ぶ。基準は選ばなくても入る（差の基準になる）。知らない名前だけで基準しか残らないときは全条件へ戻す。1 行の表を出しても何も分からないので。

```
?capture=1&sweep=1&script=enemy-eight&frame=240&nodegrade=1&hour=16&only=enemies&bench=200
```

2 条件なら総量が 10 分の 1 になる。試料を増やしても熱が乗らない。見出しに「2 条件 x 試料 200 回」と出る。

### 雲を切った上で比べる

**雲は GPU 時間の最大項で、ばらつきの主因でもある。**実機で 5.97〜9.00 ms。敵機の差はどの回もばらつきの内側だった（−1.09 / −2.05 ms 対 ばらつき 3.84 / 6.01 ms）。

そこで「雲なし」と「雲なし＋敵機なし」を並べる条件を用意した。

```
?capture=1&sweep=1&script=enemy-eight&frame=240&nodegrade=1&hour=16&only=clouds,cloudsenemies&bench=200
```

**敵機の費用は「雲なし」と「雲なし＋敵機なし」の引き算で取る。**表の差の列は基準との差なので、そこは手で引く。三角形が 599k と 474k に分かれていれば、切れていることは確かめられる。

雲を足した状態の合計は、この差を「雲あり」の基準に足して見積もる。GPU が直列に律速している限りは加算で足りる。**それでも遊べるかどうかはライブループで見る。**

### 実測（2026-08-24、6 回目）

Intel Arc 140V / preset high / 1920 x 946 / `enemy-eight` f240 / 3 条件 × 試料 200 回。

| 条件 | GPU 最小 | CPU 最小 | 三角形 | 判定 |
|---|---|---|---|---|
| 基準 | 7.76 ms | 9.90 ms | 599k | — |
| 雲なし | 4.58 ms | 6.40 ms | 599k | 有意 |
| 雲なし＋敵機なし | 4.34 ms | 5.80 ms | 474k | 有意 |

**敵 8 機で GPU 0.24 ms、CPU 0.60 ms。**ばらつきの目安は 0.45 ms なので、GPU は「0.45 ms より小さい」までしか言えない。CPU の 0.60 ms は外側なので読める。三角形は 125k（1 機あたり 15.6k）。

ばらつきは 6.01 → 1.65 → 0.45 ms と下がった。**条件を絞ることと雲を切ることの両方が効いている。**

雲は 3.18 ms で GPU の 41%。

### ライブループの実測（同じ日、同じ機械）

`?debug=1&script=enemy-eight` を開いて読んだ。1920 x 946 / DPR 1.50 なので実描画は 2880 x 1419 相当。

```
FPS 60 (16.7 ms)

うち雲    2.2 / 最大 5.6 ms

```

**敵機込みで 60 fps が出ている。**余裕は 10.2 ms（予算の 61%）、最大の 9.8 ms でも 6.9 ms 残る。

三角形の裏も取れる。投入 613k から地形 451k と自機 18.6k を引くと 143.4k。うち敵 8 機ぶんが 124.8k（15.6k × 8）で、sweep で測った 125k と一致する。残り 18.6k は海面と軌跡と雲の板。

**60 fps が出るかは sweep では判定しない。**sweep は vsync を待たずに描き続けるので、遊んでいるときより負荷の掛け方が重い。`?debug=1` のライブループが GPU 時間と最大を 16.7 ms と並べて出すので、そちらで見る。

## 「有意」が 1 つも無い表は読めない（2026-08-24 実測）

欠陥を直したあと、実機で 3 度目を回した。**構造は正しくなった。**見出しは「敵機 8 機」、三角形は基準 599k・敵機なし 474k で分かれる。全条件が実際に切れている。

それでも読めなかった。ばらつきの目安 3.84 ms に対して、いちばん大きい差が後処理だけの −2.24 ms。**「有意」の行が 1 つも無い。**

| 条件 | GPU 最小 | 基準との差 | 三角形 |
|---|---|---|---|
| 基準 | 7.01 ms | — | 599k |

CPU の列も同じ。「敵機なし」は −2.30 ms。CPU をほとんど減らさないはずの「海面なし」が −2.20、「環境反射なし」が −1.90、`cells 24` が −1.90 で並ぶ。`lod 0.65` は +2.30。分離できない。

**騒がしさは GPU 中央と最小の差に出る。**基準は 7.01 と 11.30 で 4.29 ms 開いている。3 回のばらつきは 0.35 → 0.94 → 3.84 ms。同じ機械なので、環境が違う。

表が自分で言うようにした。「有意」が 1 つも無いときは警告を出す。全行を突き合わせないと気づけない条件なので、人が読む前の段階で表に判定させる。

判定は `bench.ts` の純関数（`benchNoiseFloor` / `benchBestGain` / `benchUnreadable`）。表の判定列と警告で同じ値を使う。別々に書くと食い違う。

**発火は絵では確かめられない。**SwiftShader は騒がしいが、後処理の差が桁で出る（実測でばらつき 493.29 ms・後処理だけ −513.39 ms）。だから「読める」と判定されて警告が出ない。`tests/render/benchVerdict.test.ts` が実機の 21 行をそのまま入れて発火を固定する。**部分集合では中央値が合わない**（6 行に削ったら 3.80 になった）。

測り直すときは、ほかの負荷を止め、電源につないで、`?bench=120` のように試料を増やす（既定は 40）。見出しに試料の数が出る。

## 計器が嘘をついた例

キャプチャモードは DPR を 1 に固定している。基準画像を機械に依らせないため。実機は DPR 1.50 で画素数が 2.25 倍あるので、計測モード（`?sweep=1`）だけ実 DPR を使う。

タイマークエリの結果は同じ JavaScript タスクの中では揃わない。`gl.finish()` のあと 10 万回ポーリングしても `QUERY_RESULT_AVAILABLE` が立たない。`requestAnimationFrame` をまたいで回収する。

`gl.finish()` では Chrome の描画は同期しない。`gl.readPixels` で読み戻さないと投入時間しか測れない。全解像度が 1/4 より速いという嘘の値が出た。

## 判断の基準

GPU の最大が 16.7 ms を超えるなら、プリセットの列を下げる。下げる先は実測で決める。**推定で下げない。**「16bit にすると帯域が倍で重くなる」と見込んだことがある。実測では 16bit のほうを速く測った（Phase 3）。

## シェーダの遅延コンパイルがフレームを止めていた（2026-08-31 実測）

three がシェーダをコンパイルするのは、マテリアルを作った時点ではなく**それを持つオブジェクトを最初に描くとき**。爆発・フレア・曳光弾・ミサイルは出るまで描かれないので、初登場のフレームでまとめて走る。

`?script=mission-01` を SwiftShader で開き、フレームごとに `renderer.info.programs.length` と経過時間を記録した。

| 経過 | 増えたプログラム | そのフレーム |
|---|---|---|
| 3.47 s | +13（25 → 35） | **772.9 ms** |
| 4.22 s | +2 | 192.4 ms |
| 7.58 s | +1 | 143.4 ms |

**主犯は品質の自動降格だった。**増えた 16 個のうち 11 個が `physical`（機体のマテリアル）で、`cacheKey` を突き合わせると 41 文字目の `512` が `256` に変わっているだけだった。プリセットで影のマップ解像度が変わり、それが `getProgramCacheKey` に入る。

`PerformanceGovernor` は 3 秒連続で 55 fps を割ると 1 段落とす。SwiftShader は遅いので必ず降格する。**軽くするための降格が、その瞬間に最大のスパイクを作っていた。**

`?nodegrade=1` で降格を止めると +13 が消え、残るのは 2 個（300.0 ms）だけになった。これで原因が確定した。

### compileAsync だけでは足りない

`renderer.compileAsync(scene, camera)` を起動時に呼ぶと 25 → 43 個になったが、**ゲーム中の +13 は消えなかった。**

4 段のプリセットを順に当てて `compileAsync` を呼んでも同じだった。起動後の機体プログラムの分布を見ると `306,512` が 10 個だけで、medium 用の `306,256` は 1 つも作られていない。

影の状態が変わったことによる作り直しは `WebGLRenderer.setProgram` の中で判定される。**描かないと起きない。**

### プリセットごとに 1 枚描く

`applyPreset(name)` のあと `compileAsync` に加えて実際に 1 枚描く。分布は `306,512` 20 個 / `306,256` 10 個 / `306,1024` 10 個になった。

| | 事前コンパイルなし | 4 段ぶん事前コンパイル |
|---|---|---|
| 最大のフレーム | 772.9 ms | **344.9 ms** |

## WebGPU が headless で描けるか（2026-08-31 実測、Phase 8 段 0）

Phase 8 は基準画像を WebGPU で撮り直す。撮れなければ E2E が丸ごと止まるので、着手の前に測った。道具は `tools/webgpu-probe.mjs`。

**adapter が取れることと描けることは別。**プローブは 320x200 に WGSL で全画面三角形を描き、2D キャンバスへ写して画素を読み戻し、シェーダの式と突き合わせるところまでやる。

| device | 取れる |

## 雲ノイズを TSL へ移した（2026-09-01 実測、Phase 8 段 11）

`noise3d.frag` を `src/render/clouds/noiseNodes.ts` へ写した。移行全体の決定論の土台なので、画素比較ではなく数値比較で押さえる。

比べたのは 2 つ。ハッシュ（PCG3D）の上位 8 ビットを 16x16 の格子で焼いたもの 768 個と、形状ノイズの中央スライスの左下 16x16 を RGBA8 で読み戻した 1,024 個。

| 比べたもの | GLSL（既定） | node/WebGL2 | node/WebGPU |
|---|---|---|---|
| ハッシュ 768 個 対 CPU 参照 | ― | 一致 | 一致 |
| ノイズ 1,024 個 対 GLSL 版 | 基準 | 一致 | 一致 |

**浮動小数まで一致した。**計画が仕様上ビット一致すると見ていたのは整数のハッシュだけだったが、Worley と Perlin の `sqrt` `normalize` `mix` を含む合成まで、GLSL と WGSL で 1 ビットも違わなかった。

### 読み戻しの向きと原点がバックエンドで違う

3 回つまずいた。どれも算術ではなく読み戻しの側。

**行が 256 バイトへ揃う。**WebGPU で 16 px 幅（64 バイト）を 16 行読むと 3,904 バイト戻る。15 行 x 256 + 64 で、最後の行だけ揃えられない。WebGL2 は詰まったまま 1,024 バイトを返す。

**行の並びが逆。**WebGL2 は下から、WebGPU は上から返る。ハッシュの格子で、WebGPU の先頭が `hashTopByte(0, 15, 0)` に一致した。**算術は合っていて並びだけが違う**ので、気づかないと「WGSL のハッシュがずれている」と読み違える。

**原点の上下も逆。**`readRenderTargetPixelsAsync(target, 0, 0, 16, 16)` は WebGL2 では左下の角、WebGPU では左上の角を指す。64x64 の左下を読むには WebGPU 側で `y = 48` から読む。行を反転しただけでは足りなかった。

### TSL で踏んだもの

`toVar()` と `assign()` は `Fn` の中にしか置けない。素の関数の中で使うと `THREE.TSL: No stack defined for assign operation.` が出る。`worley` と `perlin` を `Fn(() => ...)()` で包んだ。

`@types/three` の整数ビット演算は `IntegerType = 'int' | 'uint'` に限られていて、`uvec3` には型が付かない（`OperatorNode.d.ts:507`）。実装は通る。成分ごとのスカラで書いたので、計画が案じていた `uvec3 >> uint` のスカラ渡しの問題も消えた。

`%` を使わずに済ませた。周波数がすべて 2 のべき乗（2, 4, 8, 16）なので `cell & (period - 1)` が `((cell % period) + period) % period` と同値になる。`tests/render/noiseWrap.test.ts` が、実際に使う周波数を本文から拾って同値を確かめる。

| 16 km | 256（据え置き） | 34.2 |
| 12 km | 256（据え置き） | 38.8 |

歩幅の profile を保ったまま距離を縮めるには、歩数も落とす。今の G から「12 km を同じ歩幅で覆う歩数」を解いた。

|---|---|---|---|
| low | 32 | 27 | 84% |
| medium | 64 | 51 | 80% |
| high | 256 | 163 | 64% |
| ultra | 384 | 214 | 56% |

対にして測ると密度サンプルはこうなる。

| 構図 | 26 km / 256 歩 | 12 km / 163 歩 | 9 km / 134 歩 |
|---|---|---|---|
| `level-afternoon` | 29.2 | 27.3 | 26.1 |
| `terrain-overlook` | 30.0 | 29.1 | 28.4 |
| `clouds-climb` | 25.6 | 23.8 | 22.6 |

**歩数は 36% 減るが、密度サンプルは 6〜7% しか減らない。**遠方は密度ゼロ区間の大股送りで進んでいるので、削られるのは安い歩のほうだった。費用の主は近景の雲の中にある。

絵は 12 km と 9 km でほとんど変わらない。飛び込みの危険が小さい 12 km を採った。撮り直しが要ったのは 42 枚のうち 12 枚。

### `--update-snapshots` は許容の内側を書き直さない

撮り直したあとに `npm run exact` が 3 枚を「動いた」と報告した。`clouds-dense` が全面 1 階調、`terrain-peak` が水平線際の帯で 8 階調、`aircraft-vortex-long` が 27 画素で 1 階調。

2 回走らせて 1 バイトも違わなかったので、実行ごとの揺れではない。原因は `--update-snapshots` の既定が `changed` で、**比較器が「変わっていない」と判断した画像は書き直さない**こと。`threshold: 0.05` は 12.75 階調まで同一とみなすので、1〜8 階調の変化はすべて許容の内側に入る。

段 6 で許容を 0 にした関門と食い違う。`--update-snapshots=all` で書き直して 42/42 へ戻した。

## 段 12 で 3D テクスチャの層を通した（2026-09-02 実測）

雲の密度と雲影を TSL へ写した。合格条件は「雲影マップ 256² を読み戻して旧経路と
ヒストグラム 16 ビンで比較し、L1 距離 0.01 未満」。**通った。**ただし合格条件
そのものに穴があったので、検査を 1 つ足している。

### 止まっていた原因は読み戻しだけだった

前日の記録は「層への焼き込みか層の読み戻しのどちらかが効いていない。WebGL2 でも
WebGPU でも同じ」だった。**後半が誤りだった。**64³ の層 0・32・63 を両バックエンドで
測り直すと、こうなる。

| 経路 | 層ごとの焼き込み | 3D から直に読み戻し |
|---|---|---|
| node / WebGPU | 効く | 効く |
| node / WebGL2 フォールバック | 効く | **全部 0** |

原因は three の実装漏れ。`WebGLTextureUtils.copyTextureToBuffer`
（`node_modules/three/src/renderers/webgl-fallback/utils/WebGLTextureUtils.js:1201`）が
キューブテクスチャ以外を `gl.TEXTURE_2D` 決め打ちで `framebufferTexture2D` へ渡す。
3D テクスチャのアタッチが `GL_INVALID_OPERATION` で失敗し、framebuffer が
incomplete のまま `readPixels` が 0 を返す。`faceIndex` は使われない。**例外は
飛ばず、GL の警告がコンソールへ出るだけ。**WebGPU 側は
`WebGPUTextureUtils.js:663` が `origin.z` を組むので効く。

切り分けは、体積をシェーダから引いて 2D のレンダーターゲットへ落とし、そちらを
読むことで付けた。2D の読み戻しは段 11 で実証済みの経路なので、焼き込みが
効いているかを独立に見られる。

**両バックエンドで効く読み方を採った。**`textureLoad`（整数フェッチ）で層を引いて
2D へ落とす。補間を跨がないので GLSL 版の読み戻しとビットで比べられる。
実装は `src/render/clouds/volume.ts` の `readVolumeSlice`。

### 上下が逆のノイズを引いていた

体積を焼いて中央スライスを読むと、GLSL 版と 1,024 バイト中 876 バイトが違った。
`uv` をそのまま焼いて読み戻すと理由が出た。

| 焼き先 | 先頭テクセルの uv |
|---|---|
| 2D のレンダーターゲット | (0.008, 0.008) |
| 3D の層 | (0.008, **0.992**) |

node 経路はレンダーターゲットのテクスチャを引くとき v を裏返す。
`TextureNode.setupUV()` が `builder.isFlipY()` のときに入れる補正で、
`GLSLNodeBuilder.isFlipY()` は `true`、`WGSLNodeBuilder` は `false`。**両方
合わせると「v = 0 は描いたときの NDC の上」という同じ約束になり、バックエンドに
よらず一貫している。**一方、既定の `WebGLRenderer` の経路は「v = 0 は NDC の下」で
引く。

つまり同じ式を同じ uv で焼くと、**node 経路の密度は GLSL 版と上下が逆のノイズを
引く。**焼く側で v を裏返して打ち消した（`noiseNodes.ts` の `bakeUv`）。
`(j + 0.5) / size` は 1/128 の倍数なので `1 - v` は浮動小数でも正確に出る。
ビット一致は保たれる。

### ヒストグラムは配置を見なかった

**この上下反転を、段 12 の合格条件は捕まえなかった。**ノイズの体積を反転した
ままでも、雲影 256² の 16 ビンのヒストグラムは L1 距離 0.01 の内側に収まる。
気象マップだけを反転しても同じだった。分布が合っていることは、影が同じ場所に
あることを意味しない。

区画ごとの平均（`shadowTileMeans`、4x4 の 16 個）を足して測り直した。

| 壊し方 | ヒストグラムの L1 | 区画平均の最大のずれ |
|---|---|---|
| 気象マップを上下反転 | 0.01 未満（通る） | **0.330**（落ちる） |
| ノイズの体積を上下反転 | 0.01 未満（通る） | 0.02 未満（通る） |

**2 つの検査は別のものを見張っている。**気象マップの反転は区画平均が捕まえ、
ノイズの反転は形状ノイズ 1,024 個のビット一致だけが捕まえる。ノイズの周期は
4,200 m で影マップの一辺 30,000 m に 7 周ぶん入るので、反転しても区画の平均は
動かない。気象マップの周期は 42,000 m なので配置がそのまま効く。

気象マップにもビット一致の検査を足した。GLSL 版は 512² の左下 16x16 を
`readRenderTargetPixels` で読み、TSL 版は同じ角を整数フェッチで読む。
**両バックエンドで 1,024 バイトが一致した。**`pcg2d` と `perlin2` と `fbm2` の
写しに誤りがないことは、これで直接言える。

段 12 の合格条件は 4 本立てにした。形状ノイズ 1,024 個のビット一致、気象マップ
1,024 個のビット一致、雲影のヒストグラム L1 距離 0.01 未満、雲影の区画平均の
最大のずれ 0.02 未満。**最初の 3 本は `?gpu=1` と `?gpu=2` の両方で回す。**

## 段 13 の 4 つの難所を先に測った（2026-09-02 実測）

計画は雲のレイマーチ本体（426 行）の難所を 4 つ挙げていた。**書く前に小さな
プローブで測った。**4 つとも WebGL2 と WebGPU の両方で確かめている。

`Loop` と `Break` と `Continue`、そして `inout int samples` に相当する
「`setLayout` を付けない `Fn` で呼び出し側の var を触る」形は、CPU 参照と
ビット一致した。**ただし `Fn` の返り値を使わないと本体が生成されない。**
最初の測定で、ループの回数は合っているのに `Fn` の中で足した counter だけが
0 のまま返った。例外も警告も出ない。

`BAYER_8X8[64]` のビット式は総当たりで確定させた。`x ^ y` と `y` の下位桁から
1 ビットずつ交互に積む形だけが元の表と一致する。最初に書いた式を含め、
試した 18 通りのうち当たりは 1 つだった。

`screenCoordinate.y` は上から数える。16 行の的で行 0 が `screenY = 15` を返す。
`gl_FragCoord.y` は下からなので、`screenSize.y - 1 - y` で揃える。**両
バックエンドとも上からで一貫している**ので、直すのは 1 か所で足りる。

## 段 13 のマーチは整数で突き合わせた（2026-09-02 実測）

固定のカメラと固定の入力を `src/render/clouds/marchProbe.ts` に 1 か所だけ

雲層の内側（y = 2,000）から水平に見る構図へ変え、雲量を 0.6 へ上げた。

## 段 14 の前半: 高さ場は 4.5 mm で一致した（2026-09-03 実測）

`heightfield.glsl` の高さ引きを TSL へ写した。**突き合わせる相手は GLSL 版では
なく `src/sim/terrain.ts` の `heightAt` そのもの。**「見えている山と当たる山が

計画は 1e-3 m を合格条件に置いていたが、**届かない。**GPU は float32 で解く。

|---|---|
| GPU（`?gpu=1`）と CPU（float64） | 4.5 mm |
| CPU の float32 と CPU の float64 | 1.03 mm |

| 壊し方 | 最大のずれ |
|---|---|
| 双三次の係数 5 を 4.99 にする | 14.18 m |
| タップの添字を 1 つずらす | 3.20 m |
| 縁で止めるのをやめる | 340.16 m |

## 段 15: 影は node 経路で立つ（2026-09-03 実測）

`BasicShadowMap` を選んだ理由（比較モードが付くと自前 GLSL の `sampler2D` から
`r` 成分を読めない）は node 経路では消える。プリセットに `shadowFilter` の列を
足し、`pcf` と `pcfSoft` が通ることを実測した。**`PCFSoftShadowFilter` は
WebGL 経路では廃止されているが node 経路には生きている。**

### 焼き込みの回数は差で数える

「影マップは 1 フレームに 1 回しか焼かれない」を確かめるのに、まずドローコール
の増分を機体のドローコールと比べようとした。**当てにならない。**

| 数え方 | 値 |
|---|---|
| 機体のメッシュの枚数 | 33 |
| 機体が払うドローコール（主カメラ） | 31 |
| 影のパスが払うドローコール | 47 |

視錐台の切り方が主カメラと影のカメラで違い、メッシュ 1 枚が複数の材質を持つと
1 回では描かれない。`info.render.frameCalls` でパスの数を数える形に替えた。

### 有効にするだけでパスが 1 つ増える

パスの数を「無効との差」で数えると、今度は WebGPU 経路で 2 回と出た。投げ手を
切ったまま有効にして測り直すと理由が出た。

| 状態 | パスの数（`?gpu=2`） |
|---|---|
| `shadowMap.enabled = false` | 1 |
| `true`、投げ手なし | **2** |
| `true`、投げ手あり | 3 |

**増えた 2 つのうち 1 つは影マップではない。**投げ手が無いのに増えている。
何が足しているかは特定できていないので、`docs/lessons.md` の穴へ入れた。
影マップの回数は「投げ手あり」と「投げ手なし」の差で数えることにした。

node 経路の WebGL2（`?gpu=1`）では、有効にするだけでは増えない（差は 0）。

### 絵の差は区画平均では見えない

機体の影は画面のごく一部しか覆わない。1280x720 を 4x4 の区画平均に均すと
**0.00028 しか動かなかった。**バイトの違いを数える形に替えた。

## 段 16: 円形スプライトはバイトまで一致した（2026-09-03 実測）

爆発とフレアの断片は `vUv` だけの関数なので、場面を組まずに全画面のクアッドへ
焼いて比べられる。`?gpu=1` は 64x64 の 2 枚（暈と芯）とも **16,384 バイトが
1 つも違わなかった。**`?gpu=2`（WGSL）も最大差 1 階調に収まる。

移す前に、GLSL の断片が `explosions.ts` と `flares.ts` に写しで置いてあったのを
1 つにまとめた（`radialSprite.ts`）。**写しが 2 つあると突き合わせる相手が
定まらない。**`explosions.ts` 側は `#ifdef` を立てないので振る舞いは変わらず、
基準画像 42 枚も動かない。

`#ifdef OPAQUE_CORE` はリポジトリで唯一の `defines` だった。TSL には前処理が
無いので JS の分岐で別の枝を組み立てる。生成時に決まるので、実行時の分岐は
残らない。`discard` は `Discard(条件)` の 1 行になる。

## 段 17 の入口: AgX は持ち越せる（2026-09-03 実測）

計画は「AgX は式が同じで、露出 6 はそのまま持ち越せる」と書いていた。
**持ち越せるなら VFX の色定数を測り直さずに済む**ので、ポストを組み直す前に
確かめた。

既定の経路は `postprocessing` の `ToneMappingEffect` を通すが、AGX モードは
`AgXToneMapping(texel)` を呼ぶだけで、実体は three の GLSL チャンク。
**比べるのは three の GLSL 版と TSL 版。**露出の渡し方だけが違い、GLSL は
`toneMappingExposure` の uniform を関数の中で読み、TSL は
`agxToneMapping(color, exposure)` の引数で受ける。

10^-3 から 10^2 までの放射輝度を 1,024 段、色の比 (1, 0.8, 0.6) で通した。

| | 値 |
|---|---|
| 違うバイト | **4,096 中 1 個** |
| 最大差 | **1 階調** |

1,024 段のうち 1 段で丸めが分かれただけで、曲線も定数も同じ。**露出 6 は
そのまま持ち越せる。**

検査の下限を置くときに一度外した。「暗部が 0 になること」を条件にしたが、
**AgX は暗部を持ち上げる**ので 10^-3 に露出 6 を掛けても 0 にはならない。
階調の幅（200 以上）と上端（250 以上）で縛る形へ直した。

## 段 17 の前半: 雲の合成はバイトまで一致した（2026-09-04 実測）

通ったかどうかは出てこない。**段 13・14・16 で 3 度踏んだ形なので、移す前に

### 除算で 1 を作ろうとして 1 列外した

最初は `min(col / 47.0, 1.0)` と書いた。列 47 で 47/47 = 1 になるはずが、
早期打ち切りを通った画素が **1,024（期待 1,088）**しかない。ちょうど 1 列
ぶん足りない。

`47 * fl(1/47) = 0.99999994` になる。列の比較で 1 を作る形へ直した。

本番はこの心配がない。雲は 8 ビットか半精度のレンダーターゲットから来るので、
完全不透明の画素は厳密に 1.0 で読める。

### 稼ぎがあることは本文で確かめた

枝を数えても、大気の組み立てが `else` の中にあるかは分からない。
`renderer.debug.getShaderAsync` で生成された本文を読んだ。

```glsl
if ( ( nodeVar3.w == 1.0 ) ) {
  nodeVar4 = nodeVar3;
} else {
  nodeVar5 = vec4( ( vec3( 0.85, 0.55, 0.2 ) * vec3( nodeVar2 ) ), 1.0 );
  nodeVar4 = vec4( ( ( nodeVar5.xyz * vec3( ( 1.0 - nodeVar3.w ) ) ) + nodeVar3.xyz ), nodeVar5.w );
```

下地の組み立てが `else` の中に 1 回だけある。**下地を関数で受ける形にした
のがこれを決めている。**値で受け取ると呼び出し側で先に組み立てられ、外へ
出てしまう。

### 引き直しの向きは裏返した絵との差で確かめた

本番の雲はレンダーターゲットから来る。node 経路は v を裏返して読むので、
そこが合っていなければ上下の裏返った雲を合成する。8 ビットのレンダー
ターゲットへ焼いてから引き直して比べた。

| 比べた相手 | 違うバイト | 最大差 |
|---|---|---|
| 解析入力の合成 | 2,279 | **1** |
| その上下を裏返したもの | 12,115 | **242** |

1 階調のずれは 1/255 刻みへの丸めで、向きとは関係がない。裏返すと 242 階調
開くので、この検査には歯がある。

していないか**を見るために置いてある。

## 段 17c の前半: 地表のライティングを LUT へ移した（2026-09-06 実測）

自前の `sunRadiance * lambert / pi + skyRadiance` を
`getSplitIlluminance(positionUnit, normalECEF, sunDirectionECEF)` へ置き換えた。
**地表と機体が同じ式で決まる。**`AtmosphereLightNode` は間接に
`getIndirectIlluminance` を使い、直達は太陽放射照度に透過率と
`max(N・L, 0)` を掛ける。`getSplitIlluminance` はその 2 つを 1 度に返す
（`getSplitIrradiance` が同じ式で組んでいる）。

### 1/pi はちょうど 1 回だけ掛かる

照度の口へ**段 17b までと同じ値を流し込んで**突き合わせた。`skyRadiance` は
放射輝度なので pi を掛けて照度へ戻す。掛け忘れや二重掛けがあれば 3.14 倍
ずれる。実測は最大差 1 階調。

### 直達は WebGL 経路の値と一致した

同じ点で法線だけを変えて焼いた。

| | R | G | B |
|---|---|---|---|
| WebGL 経路の `sunRadiance` | 1.751 | 1.381 | 1.136 |
| node の直達（太陽へ向けた面） | 1.705 | 1.312 | 1.012 |
| 比 | 0.97 | 0.95 | 0.89 |

太陽に背けた面は **3 成分とも厳密に 0。**直達に `max(N・L, 0)` が入っている
ことの裏取りになる。

### 間接は 2.7〜3.5 倍になった

| | R | G | B |
|---|---|---|---|
| WebGL 経路の `skyRadiance` | 0.00553 | 0.00928 | 0.02041 |
| node の間接 ÷ pi | 0.01941 | 0.03005 | 0.05556 |
| 比 | 3.51 | 3.24 | 2.72 |

内訳は 2 つ。**式で 1.64 倍。**WebGL 経路は `SkyLightProbe` の球面調和の
L0 だけを読んで 0.28 を掛ける（`atmosphere.ts`）。L0 は照度の
`1/sqrt(pi)` 倍なので、実質 0.158 倍の放射輝度になる。node 側は
`(1 + N・up) / 2` を pi で割るので、法線が太陽（仰角 0.63）を向いた面で
0.259 倍。比は 1.64。

**LUT そのもので 1.7〜2.1 倍。**残りは実行時に計算した照度 LUT と同梱の
EXR の差。`atmosphereLutScale` は 1 なので解像度の差ではない。ADR 0010 は
EXR を捨てると決めているので、**実行時の値が採用される側**になる。

L1 の項まで足せば `getIrradianceAt(n)` は `E * (1 + n・up) / 2` を返す。
takram の係数は `L0_COEFF = 1/sqrt(pi)` と `L1_COEFF = sqrt(3)/(2 sqrt(pi))`。
これを three の 0.886227 と 1.023328 に掛けると厳密にそうなる。
**WebGL 経路の地表だけが L0 を単独で読んでいた。**機体は球面調和をそのまま使うので、
WebGL 経路では地表と機体が食い違っていた。段 17c はそこも揃える。

### LUT ができる前に焼くと真っ黒になる

最初、ライティングの差を焼く場所を `compileAsync` より前に置いた。
**地表が 3 成分とも 0 で返った。**例外は出ない。`AtmosphereLUTNode.setup()`
が走るのは `compileAsync` の中で、中身ができるのは `updateTextures` の後。

### 場面のカメラでは差が出てこない

置き換えの差を場面の絵で測ったら **736 バイト・最大 1 階調**しか動かなかった。
プローブの構図では地表が画面をほとんど覆っておらず、映っているのは海面と
空だった。段 17b の突き合わせに使った 5 km 角で測り直すと
**12,288 バイト・最大 99 階調。**

| 区画平均 | 置き換え前 | 置き換え後 |
|---|---|---|
| 最小 | 0.0506 | 0.0051 |
| 最大 | 0.1992 | 0.1146 |

置き換え前は段 17b の仮置き（雲のマーチの固定入力）なので、**この暗く
なった比は WebGL 経路との差ではない。**仮置きの環境光 0.28 が実際の
天空照度より 14 倍大きかったぶんが落ちている。

## 段 17c の後半: 海面と雲と影を繋いだ（2026-09-06 実測）

海面と雲の放射輝度も LUT から取り、機体の影を `shadow(light)` で地形と
海面へ引き込んだ。node 経路のライティングはこれで CPU 側の値を 1 つも
読まなくなった。

### 海面は照度ではなく放射輝度で書いてある

反射の 3 倍、body の 0.12、白波の 0.30、スペキュラの 0.9。どれも放射輝度に
対して調整してあるので、**値の出どころだけを差し替えて式は動かさない。**

太陽は余弦を含まない側（`getSplitScalarIlluminance`）を使う。スペキュラは
太陽の見かけの明るさで決まるので、面の傾きで暗くしてはいけない。天空は
半球の重みが要るので `getSplitIlluminance` の間接を pi で割る。

雲も同じ。**原点の海面高度で 1 度だけ引く。**大気は緩やかにしか変わらず、
GLSL 経路もフレームに 1 つの値を uniform で渡していた。

### 影は光の `castShadow` を立てる順で決まった

`shadow(light)` を地形の材質へ入れたら `compileAsync` の中で落ちた。

```
TypeError: Cannot read properties of null (reading 'depthTexture')
  at ShadowNode.updateShadow
  at ShadowNode.updateBefore
  at Renderer.compileAsync
```

`ShadowNode.setup()` は `Fn` の中で `setupShadow` を呼ぶ。**本体が生成
されるまで `shadowMap` は null。**`updateBefore` だけが先に走ると触る。

落ちていたのは自前で呼んだノードではなかった。**組み立ての時点で光に
`castShadow` が立っていると、three の光の系が影のノードをもう 1 つ作る。**
その本体は光の寄与が畳まれると生成されない。`AtmosphereLight`（takram が
`setupDirect` を差し替えている）でも、明るさ 0 の指向光でも同じだった。

順で解いた。組み立てのあいだは `castShadow` を伏せ、`compileAsync` の
あとで立てる。**伏せたままでは影マップが焼かれない**ので、立てる側も要る
（伏せたまま測ると最大差 1 階調しか出なかった）。

| 測ったもの | 値 |
|---|---|
| 投げ手を切って動いた画素 | 2,056 バイト |
| 最大差 | **71 階調** |
| 影あり／なしのパスの数 | 13 / 13 |
| 描画呼び出し | 64 → 150 |
| 定常の 1 枚 | 777 → 811 ms |

**パスの数では分からない。**投げ手が無くても影のパスは走る（段 15 と同じ）。
数えるのは投げ手を切った絵の差。

GLSL 経路の `terrainAircraftShade` にあった 0.35 の下限は入れていない。
照度の形では間接がそのまま残るので、直達を 0 にしても真っ暗にならない。
**下限は自前ライティングの都合だった。**

## 段 18 の前半: 計測の口をバックエンドへ寄せた（2026-09-06 実測）

**交互計測をやめた。**`TIME_ELAPSED` のクエリは入れ子にできないので、
フレーム全体と雲のパスを 1 フレームおきに交互で測っていた。内訳は

## 段 18 の後半: node 経路の GPU 時間が取れた（2026-09-06 実測）

WebGL2 の `EXT_disjoint_timer_query_webgl2` は node 経路に無い。
`renderer.resolveTimestampsAsync()` が返す ms を使う。レンダラは
`{ trackTimestamp: true }` で作る。

| 経路 | 回収できた件数 | GPU 最小 | CPU（排出込み） |
|---|---|---|---|
| `?gpu=1`（node/WebGL2） | 8 / 8 | **11.0 ms** | 16.2 ms |
| `?gpu=2`（WebGPU） | 8 / 8 | **229.9 ms** | 231.9 ms |

`?gpu=1` は glb だけ、`?gpu=2` は大気まで組んだ場面なので、値は比べない。
**どちらの経路でも数が返ることが確かめられた**のがこの段の要点。

`?gpu=1` の GPU と CPU の差（11.0 対 16.2）は読み戻しの排出ぶん。
`?gpu=2` は SwiftShader が CPU 律速なのでほぼ並ぶ。

### 測れないことは件数で判定する

**`trackTimestamp` は静かに false になる。**`device.features` に
`timestamp-query` が無い環境では、`{ trackTimestamp: true }` で作っても
有効にならず、`resolveTimestampsAsync()` が `undefined` を返す。例外は
出ない。これを知らずに「GPU 時間が 0」を不具合として追うと時間を溶かす
（ADR 0010 の段 0 の注記）。

数を作らずに捨てる形にしたので、**回収できた件数がそのまま「測れたか」**
になる。`tests/e2e/node-path.spec.ts` が両経路で 4 件以上を要求する。

### 排出できない表は読めない

`BenchRow` に `cpuSynchronous` を足した。**WebGPU バックエンドでは
`getContext()` が `undefined`** なので `gl.finish()` + `readPixels` の排出が
できない。排出できないと CPU 側は投入までの時間しか測っていない
（`bench.ts` が記録している罠。実測で 0.7 ms が出た）。

`benchUnreadable` に「GPU 値が全部 null で、排出もできない表は読めない」を
足した。**差が大きく出ていても読めない。**値そのものが意味を持たないため。
排出できれば GPU タイマーが無くても差で読めるし、排出できなくても GPU
タイマーがあれば読める。3 通りとも単体テストで固定した。

## 段 19 のあと: GPU 時間に 0 が混ざっていた

通し実行の E2E で `node/WebGL2 で GPU 時間が取れる` が 1 本だけ落ちた。
`gpuFrameMs` が 0。回収件数の検査（4 件以上）は通っている。同じテストを
単独で回すと通る。**競合に依存する落ち方。**

原因は three の解決の作りにある。WebGL2 のクエリは 1 本ずつ独立した物なので
何本でも同時に飛ばせるが、`resolveTimestampsAsync()` の器は 1 つしかない。

| 呼んだとき | 返る物 |
|---|---|
| 決着前に重ねた | WebGL は `lastValue`、WebGPU は走っている promise |
| 解決する物が無い | `lastValue` |
| GPU の状態が乱れていた | `lastValue` |
| `timestamp-query` が無い | `undefined` |

`lastValue` の初期値は 0（`TimestampQueryPool.js:62`）。段 18 の実装は
`undefined` だけを捨てて 0 は数に入れていたので、代表値の `Math.min` が
そのまま 0 になった。**0 でない側も危ない。**2 回目以降は「前の回の値」が
今の回の札で入るので、掃引の条件ごとの数が入れ替わる。

直し方は 3 つ。決着するまで次を投げない。0 と `undefined` はどちらも数を
作らずに捨てる。捨てた回数を `dropped` で数えて外から見えるようにする。
プローブ側は 1 枚ごとに決着を待ってから次の枚へ進む（待ちは `renderMs` の
外側なので、測った時間には入らない）。

8 ワーカーで 24 本を同時に回して確かめた。**18 本すべてで回収 8 件・破棄 0
件。**GPU 時間は WebGL2 が 20.3〜107.0 ms、WebGPU が 271.7〜1,080.5 ms。
単独実測（段 18）の WebGL2 11.0 ms より大きいのは競合ぶん。

競合は E2E では固定できないので、判定は `tests/render/nodeTimer.test.ts` が
擬似のレンダラで台本どおりに持つ。歯型は `node-timer-keep-zero` と
`node-timer-overlap-resolve`。

## 段 20 の前に: シャードは薄めただけで釣り合っていなかった

| 最長の台（7 番） | 1,221 | 631 秒 | **631 秒** |

### 10 分割で 1 台が落ちた。上限ではなくテスト自身の待ち

## 段 20a-3 の障害: 放射輝度に CPU 側の値が無い

`ScenePipeline.sunRadiance` と `skyRadiance` は `hook` へ出て E2E が見る。
`tests/e2e/smoke.spec.ts` の `太陽光の色が時刻で変わる` が 3 つ主張する。

| 主張 | 意味 |
|---|---|
| `sunRadiance[0] > 0` | 値が入っている |
| `sunRadiance[0]` が `[2]` と一致しない | 白 (1,1,1) で固定されていない |
| 夕方の r/b が朝より大きい | 時刻で色が動いている |

これは画素に依存しない 231 件のうちの 1 件で、**計画が段 20 の前提に置いた
「両経路で緑」に含まれる。**

GLSL 経路は takram の `SunDirectionalLight` が CPU 側で色を持つので
`sunLight.color` を読める（`atmosphere.ts:223`）。**node 経路には無い。**
`AtmosphereLight extends DirectionalLight` の `direct` と `indirect` は
`UniformNode<boolean>` の on/off で、色ではない。`.color` は
`DirectionalLight` の既定の白のまま残り、実際の放射輝度はシェーダが決める。

つまり何もしなければ `[0, 0, 0]` が出て、この 1 件は落ちる。**移植の欠陥
ではなく、値の置き場所が違う。**計画は「赤いならバックエンドの差ではなく
移植の欠陥」と書いているが、ここはそのどちらでもない 3 つめの場合にあたる。

取り出す手は既にある。プローブが `?nodepipeline=1` で照度を焼いて読み戻し、
GLSL 経路の値と突き合わせている。**実測で直達が 1.705 対 1.751（2.6%
違い）。**E2E が比を 0.8〜1.2 で縛っているので、同じ手で取れば
`太陽光の色が時刻で変わる` の 3 つの主張はそのまま成立する。

そこで `createNodePipeline` は照度を 1 点で焼いて読み戻し、`sunRadiance` と
`skyRadiance` に入れる。**毎フレームは焼かない。**太陽が動いたとき
（`setHour`）と要求されたときだけにする。読み戻しは非同期なので値は数枚
遅れるが、計器と検査の用途では足りる。

## 段 20a-4: 差分の台帳（1 段目 — 総量）

計画は撮り直す前にこう求めている。

> 差分の理由をあらかじめ台帳にする。（中略）**理由の付かない差分が 1 枚でも
> 残っている間は撮り直さない。**

`tools/pathdiff.mjs` が 42 枚の構図を `?gpu=3` で撮り、committed の基準画像と
比べる。`exact.mjs` は「1 画素も動いていないこと」を見る道具で判定が 0 か 1
しかないので、**動く前提の道具**を別に作った。

### 全 42 枚が動く

| | 値 |
|---|---|
| 差分画素の割合 | 99.80〜100.00% |
| 最大階調 | 126〜226 |
| 平均階調 | 6.00〜38.07（全体の平均 19.14） |

計画の見込み（大気の LUT と空のポスト化で 42 枚、un/premultiply と SMAA で
42 枚）と一致する。**動いていない枚は無い。**

平均がいちばん小さいのは `aircraft-shadow`（6.00）、`terrain-peak`（8.93）、
`bank-left-dusk`（10.84）。大きいのは `clouds-dense`（38.07）、
`aircraft-vortex-end`（31.77）、`aircraft-vortex-turn`（31.62）。

### 空の差は構図に依らず一定

**最大階調 176 で揃う群が 16 枚ある。**その 16 枚の上帯の平均は
11.54〜11.65 に収まり（幅 0.11）、下帯は 13.73〜19.10 と散る。

16 枚は HUD・敵機・武装の構図で、同じ時刻・同じ高度の水平飛行から撮って
いる。**空が同一なら空の差も同一**ということで、大気の変更が単一の原因と
して効いている裏付けになる。下帯だけが散るのは、地表と海面の見え方が
構図ごとに違うぶん。

### 平均を出す理由

画素数と最大階調だけでは「全面が薄く動いた」と「一部が大きく動いた」を
区別できない。差分画素が 99.8% を超えるのは全枚に共通なので、**枚の性格は
平均でしか読めない。**上下の帯を分けるのも同じ理由で、空（上）と地表・海面
（下）のどちらが動いたかが原因の切り分けになる。

### 並列化は効かない

8 枚を撮る時間を本数で振った。

| 本数 | 所要 |
|---|---|
| 1 | 119.4 秒 / 150.4 秒（同じ設定を 2 回） |
| 2 | 139.8 秒 |
| 4 | 137.8 秒 |

**同じ設定の 2 回が 26% ばらつく**ので、本数の差はその中に埋もれる。node
経路の 1 ページが既に機械を使い切っている（SwiftShader の Vulkan が自分で
複数のスレッドを使う）。`playwright.config.ts` の「芯数の半分が最適」は
GLSL 経路で測った値で、node 経路には当たらない。出た数値は 4 通りとも
同一なので、並列そのものは正しく動いている。速くならないだけ。

短縮できるのは**回数**のほう。`--against` は 1 枚につき 2 回撮るが、素の側は
原因を振っても同じなので `--cache` に置いて使い回す。原因 3 つを測るなら
294 回が 168 回になる（43% 減）。**ばらつきに埋もれない、算術で確定する削減。**

同一になるということで、単一の原因が空の差を作っている。上帯の総平均
16.36 のうち 11.6 前後がこれにあたる。

各原因の寄与は画素ごとの最大差の平均なので、**厳密には足し算にならない。**
比率は目安として読む。

### 撮り直しの判断

計画は「理由の付かない差分が 1 枚でも残っている間は撮り直さない」と書く。
42 枚すべてに理由が付いた。主因は大気の経路（96%）で、これは移行の目的
そのもの（LUT を実行時に計算する）。ライティングと環境反射と PCF は絵に
ほとんど出ない。SMAA は差を縮める側。

**理由の付かない差分は無い。**段 20b（撮り直し・不可逆）の前提は満たした。
